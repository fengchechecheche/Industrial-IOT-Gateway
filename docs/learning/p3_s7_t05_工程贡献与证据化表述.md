## 1. 本工作块解决什么问题

写完项目并不等于可以随意概括项目。源码能够证明“存在某项实现”，测试能够证明“在指定条件下得到某个结果”，发布则还需要稳定候选、安装产物、许可证和分发动作。T05 用表述台账（claim ledger）把这几层分开，使每个简历句子都可以回答：依据是什么、适用于哪个平台、哪些内容不是自己实现、哪些结论尚未成立。

本项目当前的可靠结论是：Linux x86_64 软件 MVP 已完成正式软件验收和可复现 bundle；Raspberry Pi 4B ARM64 已完成原生构建与 systemd 软件验收；真实 RS485/CAN 硬件、ARM64 长稳、ARM64 bundle 和公开 Release 尚未完成。

## 2. 术语与状态模型

- **事实（fact）**：从源码、合同、测试结果或发布记录直接读取的原子信息。
- **表述（claim）**：准备写入简历、项目介绍或面试回答的完整句子。
- **限定词（qualifier）**：说明平台、测试环境、次数或未覆盖范围，例如“Linux x86_64 PTY 软件仿真”。
- **测试预言机（test oracle）**：机器用于判断场景成功或失败的规则。
- **可追溯性（traceability）**：从表述反向找到事实、正式文档、run ID 和机器结果的能力。

本项目使用六种状态：`VERIFIED_IMPLEMENTATION` 只证明实现存在；`VERIFIED_RESULT` 证明正式测试结果；`INHERITED_RESULT` 表示经明确继承审查沿用旧结果；`NOT_RUN_OPTIONAL` 表示可选但未运行；`KNOWN_LIMITATION` 表示已知缺口；`REJECTED_CLAIM` 表示该句话不得使用。

## 3. 从代码到公开表述的数据流

```text
源码/合同
  -> 单元与集成测试
  -> 正式 run 的 summary/failures/SHA256SUMS
  -> 验收报告
  -> P3-Fxxx 事实
  -> P3-Cxxx 表述
  -> 简历/项目介绍/面试渠道
```

每一步只能保留或缩小结论，不能扩大结论。例如，PTY 验证了字节流、超时和进程恢复逻辑，但没有生成 RS485 差分电压，因此最终表述仍必须写“PTY 软件仿真”。

## 4. 本项目中的个人实现与外部能力

个人实现集中在网关业务逻辑：Modbus 子集编解码、轮询调度、可靠性策略、质量状态、有界队列、MQTT 消息合同与适配、结构化日志、runner 和证据组织。

Eclipse Paho 提供 MQTT 客户端协议实现；Mosquitto 提供测试 broker；yaml-cpp 与 nlohmann/json 提供数据解析/序列化；GoogleTest/CTest 提供测试框架；Linux PTY/termios 和 systemd 提供操作系统能力。正确说法是“基于”“集成”“封装”和“编排”，不是“从零自研这些组件”。

## 5. 十组核心问答

### 5.1 Claim ledger 为什么不是普通项目总结？

**短答：** 普通总结追求易读，claim ledger 追求机器可查和不可越界。它为每句话记录事实 ID、证据、指标、允许渠道、限定词和禁止措辞。

**详细解释：** “实现 MQTT 上行”可以由源码证明；“8 小时无故障”必须由正式长稳 run 证明；“工业现场可靠”还需要真实硬件、环境和长期统计。把这些内容写在一个自由段落里容易发生状态升级。ledger 让每个 claim 独立审计，也保留被拒绝句子的 tombstone，避免未来重复使用同一 ID 表示不同含义。

**证据：** `P3-S7-T05_claim_ledger.yaml`，`P3-C001`～`P3-C014`。  
**允许表述：** “建立事实—claim—证据的可追溯台账。”  
**禁止表述：** “台账本身证明项目已经生产可用。”

### 5.2 “已实现”“测试通过”“正式验收”和“已发布”有什么区别？

**短答：** 已实现看源码，测试通过看某次测试，正式验收还要求冻结候选与完整判定，已发布则必须真的创建并分发版本产物。

**详细解释：** `VERIFIED_IMPLEMENTATION` 不自动附带性能数字；`VERIFIED_RESULT` 必须写清候选、环境和 run。正式验收还要求失败列表、退出码、清理状态和哈希满足合同。bundle ready 只说明安装产物可复演；未创建 Git tag、未上传 GitHub Release，就不能写“已发布”。

**证据：** `P3-F001`～`P3-F013`、`P3-F017`。  
**允许表述：** “Linux x86_64 bundle ready，尚未公开发布。”  
**禁止表述：** “v0.1.0 已上线。”

### 5.3 G4 为什么可以被最终候选继承？

**短答：** 因为最终候选的正式报告明确记录候选身份、继承边界和未改变的产品语义，并保留原始 G4 run。

**详细解释：** 继承不是简单复制 PASS。它要求后续差异不会改变被测行为，报告能追踪到原始 run，并且限定平台仍是 Linux x86_64、PTY 与本地 Mosquitto。本项目最终引用的正式 G4 是 `20260813T213614Z_soak_release_dd671cf_001`：持续 28800.046 秒，224/224 个强制 oracle 通过。它不能被继承到 ARM64 长稳或真实硬件。

**证据：** `P3-F008`、`P3-C004`、`docs/p3_s7_t04_validation.md`。  
**允许表述：** “Linux x86_64 单次 8 小时正式软件长稳通过。”  
**禁止表述：** “ARM64 和现场环境也通过 8 小时长稳。”

### 5.4 PTY 能证明什么，不能证明什么？

**短答：** PTY 能模拟双向字节流和 TTY 接口，不能模拟 RS485 收发器、电气总线和现场干扰。

**详细解释：** Linux 伪终端（pseudo-terminal, PTY）主从端由内核连接，适合测试 termios、分帧、超时、断开、晚响应、进程关闭和调度。它没有 A/B 差分线、终端/偏置电阻、隔离、共模范围、EMC 或传感器测量误差，因此 G3/G4 是软件故障证据。

**证据：** `P3-F007`、`P3-F008`、`P3-F014`。  
**允许表述：** “PTY 软件故障矩阵 15/15 PASS。”  
**禁止表述：** “RS485 物理层故障矩阵通过。”

### 5.5 x86_64 虚拟机 systemd 与树莓派 ARM64 systemd 证据如何分别使用？

**短答：** x86_64 证据支持当前发布 MVP；树莓派证据支持 ARM64 原生可移植性和服务集成，二者不能拼成一个未限定的“全平台发布”。

**详细解释：** VMware G5 在 Ubuntu Server 24.04 x86_64 上验证当前 Release 候选的服务生命周期，并与 x86_64 bundle 配套。树莓派 T02 在 ARM64 的真实 PID 1/systemd 上验证相同类型的十场景，但没有 ARM64 8 小时长稳或 bundle。因此简历可以分别写两条，也可以把 ARM64 作为带限制的扩展条目。

**证据：** `P3-F009`、`P3-F010`、`P3-F011`、`P3-F012`。  
**允许表述：** “x86_64 和 Raspberry Pi ARM64 均完成各自原生 systemd 十场景软件验收。”  
**禁止表述：** “x86_64/ARM64 均已形成正式 Release。”

### 5.6 Paho、Mosquitto 与个人 MQTT 代码如何划分？

**短答：** Paho 实现 MQTT 客户端协议，Mosquitto 充当 broker；个人代码负责消息合同、队列策略、Paho 适配、重连协调、指标和网关生命周期。

**详细解释：** `mqtt::async_client` 提供非阻塞客户端操作，但不会替项目决定 telemetry/status/LWT topic、retain 规则、fresh/stale payload、有界缓存、合并策略和关闭预算。个人贡献正是这些领域逻辑和集成代码。Mosquitto 只在本地测试环境提供 broker，不随项目被称为自研服务。

**证据：** `P3-F006`、`P3-F013`、`P3-C002`、`P3-C009`。  
**允许表述：** “基于 Eclipse Paho 集成异步 MQTT 上行。”  
**禁止表述：** “自研 MQTT 协议栈和 broker。”

### 5.7 为什么 8 小时 PASS 不等于工业现场可靠？

**短答：** 单次软件长稳只覆盖冻结负载和故障模型，不能代表温度、电磁、布线、供电、设备差异和长期统计。

**详细解释：** G4 的价值在于发现泄漏、死锁、恢复失败、队列膨胀和长期错误累计，并由 224 个 oracle 自动判定。它没有覆盖月级运行、硬件老化、浪涌、EMC、长线反射、供电掉压或多批次设备。可靠性结论必须说明观察时长、样本数和边界。

**证据：** `P3-F008`、`P3-F014`。  
**允许表述：** “在指定软件环境完成单次 8 小时长稳。”  
**禁止表述：** “达到工业级高可靠或现场生产可用。”

### 5.8 简历中的 191/191、224 个 oracle 和两个 10/10 应怎样使用？

**短答：** 每个数字只能跟随自己的平台和测试类型，不能把不同 run 的数字合并成一个总通过率。

**详细解释：** ARM64 的 `191/191` 是完整 CTest；G4 的 `224/224` 是 8 小时内的强制 oracle；x86_64 G5 和 ARM64 T02 的 `10/10` 都是 systemd 场景，但运行平台不同。推荐一条简历只放一个结果中心；面试时再展开关联证据。

**证据：** `P3-F008`、`P3-F009`、`P3-F011`、`P3-F012`。  
**允许表述：** “Raspberry Pi ARM64 Release CTest 191/191；原生 systemd 10/10。”  
**禁止表述：** “全平台 435/435 测试通过”或虚构汇总通过率。

### 5.9 面试追问“为什么没有真实硬件”时怎样回答？

**短答：** 直接说明本阶段先冻结软件合同和可重复证据，硬件物料尚未齐备；PTY 结果不替代硬件，后续按独立硬件矩阵补证。

**详细解释：** 这个回答不是回避，而是展示验证分层：协议和运行时先用可控 PTY 快速覆盖边界条件；原生 systemd 验证部署生命周期；真实硬件到货后再验证串口参数、接线、电气和设备寄存器。诚实区分证据比模糊说“基本完成硬件”更可信。

**证据：** `P3-F014`、`P3-C010`。  
**允许表述：** “真实 RS485/CAN 台架为下一独立验收门。”  
**禁止表述：** “硬件只是形式，软件测试已经等价覆盖。”

### 5.10 硬件到货后怎样新增 claim，而不是回写旧证据？

**短答：** 建立新的硬件事实 ID、run ID 和验收报告，再派生新的 claim；旧 G3/G4/G5 继续保留软件限定。

**详细解释：** 新事实应记录设备型号、固件、供电、布线、串口参数、寄存器手册版本、候选提交、场景和结果。若商用传感器只验证 `0x04`，claim 就只能写该设备/功能码；若 CAN 尚未运行，则继续保持未验证。这样历史结果不会因为新硬件而被改写，失败也能被保留和解释。

**证据：** `P3-F014`～`P3-F017`、`P3-C010`～`P3-C013`。  
**允许表述：** “新增 H1 硬件 run 后补充设备限定 claim。”  
**禁止表述：** “把原 G3 的 PTY PASS 改名为硬件 PASS。”

## 6. 常见失败模式与安全边界

- **状态升级：** 从“源码存在”跳到“性能通过”，或从“bundle ready”跳到“已发布”。
- **平台拼接：** 用 x86_64 G4、ARM64 CTest 和 ARM64 systemd 拼出不存在的 ARM64 Release。
- **分母混淆：** 把 CTest 用例、长稳 oracle 和 systemd 场景相加。
- **第三方冒领：** 将 Paho、Mosquitto、systemd 或解析库写成个人实现。
- **环境消失：** 删除“PTY”“本地 Mosquitto”“VMware”后，读者会误认为真实现场。
- **一次成功外推：** 单次 8 小时 PASS 不能代表统计可靠性或工业认证。
- **隐私泄漏：** 公开材料不得包含用户名、主机名、IP、私有绝对路径、凭据或设备序列号。
