# P3-S5-T04｜Modbus RTU 晚响应隔离与公平性修复

## 1. 本修复解决什么问题

网关给从站 500 ms 响应时间，但故障从站在 650 ms 后才回复。主站在 500 ms 已经认为旧事务
结束，如果马上发送下一请求，约 150 ms 后到达的旧响应可能被当成下一事务的数据。首次一小时
预跑中，这种跨事务污染使健康从站最大 13.5 秒没有成功请求，超过 10 秒公平性门限。

本修复不是把门限改大，而是在 timeout 后建立一个有界隔离期，等待并丢弃可能迟到的旧帧，
确认总线重新静默后才发送下一请求。

## 2. 基础概念

- transaction context：事务上下文，包含当前期待的从站、功能码、地址和响应长度；
- late response：主站已经 timeout 后才到达的旧事务响应；
- cross-transaction contamination：旧帧进入新事务接收窗口；
- quarantine：隔离，暂时不发送请求，只监听并丢弃旧数据；
- frame boundary：帧边界，Modbus RTU 使用静默时间区分相邻帧；
- fairness：故障目标不能长期阻止健康从站获得轮询机会；
- starvation：某个健康从站长期得不到成功服务；
- observability：通过事件和累计计数证明内部状态实际发生过。

## 3. 旧机制为什么不够

旧代码在发送新请求前调用一次非阻塞清空：

```text
500 ms：旧请求 timeout
立即清空当前接收缓冲区——此时晚响应尚未到达
发送其他从站请求
650 ms：旧响应到达并进入新请求上下文
```

清空函数只能删除“现在已经存在”的字节，不能删除“未来才会到达”的字节。首次正式证据中，
slave 3 在 1200.503 秒 timeout，slave 1 在 1200.658 秒出现 155 ms 的
`serial_io_transient`；下一轮又出现相同的 timeout → 约 155 ms 非目标错误序列。这与
650−500≈150 ms 的晚到量吻合。

## 4. 200 ms 隔离是怎样工作的

```text
收到 response_timeout / truncated_frame
                  ↓
记录 late_response_quarantine_started
                  ↓
最多 200 ms 不发送新请求，只等待接收字节
          ┌───────┴────────┐
        没有字节          收到旧帧
          ↓                 ↓
       结束隔离       持续读取并丢弃
                            ↓
                   等待 3.5 字符静默
                            ↓
                      恢复请求调度
```

200 ms 覆盖当前故障的约 150 ms 晚到量。收到数据后不能立即恢复，因为一个 RTU 帧可能分多次
read 到达；代码要等最后一个字节之后再出现 2.006 ms 静默。为了容纳最大 256-byte ADU，整体
上限还增加约 150 ms 最大帧传输预算。

隔离必须有上限。如果无限等待，一个永久发噪声或行为异常的从站会让整条总线永远停止。

## 5. 3.5 字符时间怎样计算

19200 baud、8E1 的一个字符包含：1 起始位 + 8 数据位 + 1 校验位 + 1 停止位，共 11 bit。

```text
1 字符时间 = 11 / 19200 ≈ 0.573 ms
3.5 字符时间 ≈ 2.006 ms
256 bytes 最大传输时间 ≈ 256 × 11 / 19200 ≈ 146.7 ms
```

3.5 字符静默用于判断“已经开始到达的帧结束了”，不能用来等待一帧在 timeout 后什么时候开始。
所以代码同时需要 200 ms 首字节监听窗口和 3.5 字符结束判定。

## 6. 为什么不直接关闭再打开串口

晚帧是协议时序问题，不代表 USB 串口或 PTY 已断开。关闭健康串口会带来额外副作用：

- 丢失仍在内核缓冲区中的状态；
- 引入设备重枚举或 reopen backoff；
- 把协议异常错误计为物理 I/O 故障；
- 扩大健康从站的停顿时间。

当前实现只有 peer closed、wait/read 失败等真实 I/O 故障才要求 reopen。晚帧通过同一已打开的
串口被隔离和丢弃。

## 7. 如何证明根因已经修复

只看到“最后测试 PASS”是不够的。本项目使用四层证据：

1. 旧正式证据显示 timeout 后约 155 ms 出现非目标错误和 13.5 秒饥饿；
2. 源码审计证明旧清空只处理调用时已到达的字节；
3. PTY 定向测试要求 timeout 后隔离计数增加、至少丢弃一个完整响应、健康串口不重开；
4. soak summary 要求每个 delayed 循环出现 `late_response_discarded`，否则强制 FAIL。

因此以后即使公平性偶然通过，只要没有证明晚帧实际被隔离，正式测试仍不能 PASS。

## 8. 公平性门限为什么仍是 10 秒

当前每个故障持续 15 秒。如果门限改成 20 秒，即使健康从站在整个窗口零成功，最大间隔也不
超过 15 秒，测试仍会通过，oracle 就失去意义。

健康点位的轮询周期约 200～1000 ms，新鲜度门限约 600～15000 ms。10 秒已经给重试、退避和
故障处理留了较大余量，同时还能发现明显饥饿。门限应来自业务和测试设计，不能为了让一次失败
变绿而事后放宽。

## 9. 5 GiB 证据预算为什么可以调整

首次一小时预跑外推 8 小时约 1.142 GiB，超过旧 1 GiB，但日志轮转和系统剩余磁盘均正常。
这表示预算本身过紧，而不是网关出现无界增长。v2 把总量改为 5 GiB，同时提高启动/运行时剩余
磁盘门限到 10/5 GiB，并继续保持单段 64 MiB。

这是版本化容量决策，不会修改旧 v1 profile，也不会把首次 FAIL 改写成 PASS。

- [GoogleTest](https://google.github.io/googletest/)：定向集成测试和断言设计。

真实项目中还应查阅具体从站手册的最大响应时间。如果设备允许超过当前 timeout 才正常应答，
应重新设计 timeout 合同；隔离机制负责防止异常响应污染后续事务，不应替代设备时序规格。
