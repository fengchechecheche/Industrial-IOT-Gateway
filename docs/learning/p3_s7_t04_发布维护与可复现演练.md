## 1. 本工作块解决什么问题

前面的工作块已经让网关具备 Modbus RTU 轮询、PTY 仿真、MQTT 上行、故障注入和长稳测试
能力，但“代码能运行”还不等于“已经形成稳定 Release”。P3-S7-T04 要解决的是交付链问题：

1. 哪个精确 Git 提交是发布源码；
2. 能否从清洁目录重新完成构建、测试、演示和安装；
3. 安装树中究竟包含哪些文件，每个文件是否可校验；
4. systemd 服务能否在原生 Linux 上完成启动、停止、重启和失败处理；
5. 软件证据与尚未执行的真实 RS485/CAN 硬件验证怎样分开陈述。

最终候选 `d2bcfde93b69dd7ebcf79d3901692235b2ae4df9` 已完成自动化合同、WSL2 开发预检、
正式 8 小时 G4、原生 systemd G5 十场景和稳定 bundle 清洁复演。本工作块因此可以判定 PASS；
但“稳定 bundle 已就绪”不等于已经创建 Git tag、上传 GitHub Release 或验证真实硬件。

## 2. 基础术语

### 2.1 Release、Release candidate 与 Git 提交

- **Release**：面向使用者交付、已经满足冻结验收门的版本。
- **Release candidate（RC，发布候选版）**：准备接受正式复验的候选内容，仍可能因阻塞项而
  被否决。
- **Git 提交**：一份可用 40 位提交 ID 标识的源码快照。

版本名 `v0.1.0` 描述产品版本，提交 ID 描述具体源码。只有当构建、测试、安装树、manifest、
systemd 证据和 bundle 都绑定同一个候选提交时，才能回答“这个 Release 是由哪份代码产生的”。

历史 WSL2 CP2 预检的参数使用 T02 起点提交
`4af261498a6c2561c6085a2f1ca57ef68924ea17`，但环境记录明确写着
`release_candidate_bound=false`。原因是 CP2 实现尚未由用户提交；因此这次结果只能证明当前
开发内容通过了预检，不能证明一个可重新导出的候选提交已经通过。后续正式 G4、G5、manifest
和 bundle 已重新绑定最终候选 `d2bcfde...`，没有把该历史预检升级成正式证据。

### 2.2 清洁构建（clean build）

清洁构建从不存在的构建目录开始。这样可以避免旧 `.o` 文件、旧 CMake cache、本机临时配置或
已经删除的源文件继续影响结果。

当前 runner 要求 `build/t04-preflight` 在启动前不存在，并为以下配置创建独立子目录：

```text
build/t04-preflight/
├── debug/
├── asan/
├── release/
├── tsan/
├── mqtt_off/
├── tidy/
├── demo/
└── stage/
```

目录已存在时 runner 直接拒绝执行，不会覆盖旧构建。这同时防止“新结果其实混用了旧产物”。

### 2.3 安装树、归档和 bundle

- **安装树（install tree）**：执行 `cmake --install` 后形成的目标目录结构。
- **归档（archive）**：把一组文件保存为 `tar` 等容器。
- **bundle**：交付给使用者的完整发布包，通常还需要 manifest、校验和与说明文件。

最终稳定包为 `industrial_iot_gateway-0.1.0-linux-x86_64.tar.gz`。包内安装树包含
`gateway_app`、systemd unit、环境样例、两份配置、LICENSE、NOTICE、README 和 runbook，共
9 个必需文件。打包前执行两次独立 `cmake --install`，规范化 tar 的顺序、mtime、owner/group
和 gzip header 后，两份归档 SHA-256 完全一致。

### 2.4 Manifest 与 SHA-256

manifest 是“包内有什么”的机器可读清单。当前 `tools/release/manifest.py` 为每个条目记录：

- 相对路径；
- 文件类型；
- Unix 权限模式；
- 字节数；
- SHA-256；
- 发布名、完整源码提交、环境分类和 G1～G6 状态。

SHA-256 能检测文件内容是否变化，但不能自行证明文件作者可信，也不能代替数字签名。当前
`SHA256SUMS` 用于完整性复核，不应被描述成发布者身份认证。

## 3. CMake 四个阶段的边界

### 3.1 Configure

`cmake -S ... -B ...` 读取 `CMakeLists.txt`、探测依赖并生成构建规则。它证明“配置可以生成”，
不证明程序已经编译或测试。

### 3.2 Build

`cmake --build ...` 调用 Ninja 和编译器生成目标。当前开启 warnings-as-errors，编译告警会成为
构建失败。

### 3.3 Test

`ctest --test-dir ... --output-on-failure --no-tests=error` 执行 CTest 注册的测试。`--no-tests=error`
避免测试注册意外为空时仍返回成功。当前 MQTT ON 配置为 188 项，MQTT OFF 配置为 176 项；
runner 从真实输出采集数量，不把数字写死在代码里。

### 3.4 Install

`cmake --install ... --prefix .../stage/usr/local` 把目标复制成拟交付的目录布局。安装通过不代表
服务已经在宿主机启动；它只证明安装规则可以产生所需文件。

## 4. 当前 release runner 的执行过程

`tools/release/release_runner.py` 当前只接受模式 `wsl-preflight`，主要路径如下：

```text
校验版本、40 位提交和路径边界
  → 确认参数提交等于当前 HEAD
  → 创建唯一证据目录并写 IN_PROGRESS
  → 识别 WSL2 环境
  → Debug + 188 CTest
  → ASan/UBSan + 188 CTest
  → Release + 188 CTest
  → TSan + 188 CTest
  → MQTT OFF + 176 CTest
  → clang-tidy / clang-format / py_compile
  → PTY+MQTT demo
  → CMake 临时安装
  → 对 staging 内 unit 做 systemd-analyze verify
  → 生成安装 manifest、SHA256SUMS 和敏感信息扫描
  → 写 summary、failures 和 PASS
```

每个外部命令都以参数数组运行，不使用 shell 字符串拼接；命令、起始时间、耗时、返回码、超时
状态和 stdout/stderr 都写入独立证据。任何强制步骤失败都会返回非零并保留失败证据。

证据默认路径冻结为：

```text
artifacts/releases/v0.1.0/<UTC时间>_<短提交>_<序号>/
```

runner 不覆盖已有 run。正式证据目录被 `.gitignore` 忽略，避免把二进制、环境详情和大日志
混入源码提交。

## 5. 为什么需要多套构建和质量门

### 5.1 Debug 与 Release

Debug 便于暴露断言和调试信息；Release 使用优化设置，可能表现出不同的时序和未定义行为。
两者都通过才能减少“只在一种编译模式可用”的风险。

### 5.2 ASan/UBSan

AddressSanitizer 检测越界、use-after-free 等内存问题，UndefinedBehaviorSanitizer 检测部分未定义
行为。它们不是形式化证明，但能覆盖普通测试很难从返回值看出的错误。

### 5.3 TSan

ThreadSanitizer 用于发现多线程数据竞争。T04 实施时，原测试用 Paho C++ 的第二个异步客户端
在 TSan 下暴露第三方消费接口的数据竞争和锁顺序问题。当前测试改为让独立 `mosquitto_sub`
进程观察 broker 上的 topic/payload，仍保留端到端发布验证，同时避免测试观察器与被测线程共享
Paho 客户端状态。

### 5.4 clang-tidy 与 clang-format

clang-tidy 检查常见 C++ 缺陷和可维护性问题；clang-format `--dry-run --Werror` 检查全项目格式。
前者关注语义模式，后者关注确定的排版合同，二者不能互相替代。

## 6. 关闭取消为何不是串口故障

T04 的 ASan 重复运行暴露了一个时序问题：当 `request_stop()` 恰好发生在串口写入或接收过程中，
运行时会把主动关闭误记为 `serial_io_transient`，并增加 `serial_errors`。

当前最小修复是在写入失败或接收结束后先检查停止请求：如果正在关闭，结果改为
`shutdown_cancelled`，不关闭串口、不增加串口错误计数。新增 PTY 测试证明“飞行中的请求被关闭
取消”与“物理串口 I/O 失败”是不同类别。

随后 soak 汇总器也必须理解新类别：

- `shutdown_cancelled` 是已知结果，不属于 unclassified error；
- 它不进入正常运行成功率和吞吐量样本；
- 它仍保留在结构化请求日志中，关闭行为可追踪。

这体现了一个重要原则：添加新的运行时结果类型时，日志、统计、验收预言机和教程必须一起更新。

## 7. systemd 在本项目中的角色

### 7.1 PID 1 与服务管理

原生 Linux 启动后，systemd 作为 PID 1 管理服务生命周期。unit 描述服务用户、启动命令、重启
策略、停止预算、安全限制和日志出口。

项目 unit 的关键合同包括：

- `User=iot-gw`、`Group=iot-gw`；
- `Restart=on-failure`、`RestartSec=2s`；
- `StartLimitBurst=5`；
- `RestartPreventExitStatus=2 3 4 5 6 7`；
- `TimeoutStopSec=5s`、`KillSignal=SIGTERM`；
- `NoNewPrivileges=true`、`ProtectSystem=strict` 等加固项。

### 7.2 staging 静态校验

直接对源码树中的 unit 执行 `systemd-analyze verify` 会查找宿主机的
`/usr/local/bin/gateway_app`，而 CP2 没有把程序安装进 WSL2 系统目录。正确做法是把 staging
作为替代根，并使用 `--recursive-errors=no`，让静态检查同时看到临时安装的 unit 和程序路径。

这只证明 unit 可以被解析且目标文件存在，不证明 start/stop/restart/journal 场景已经运行。

### 7.3 为什么 WSL2 不能关闭 G5

即使当前 WSL2 的 PID 1 是 systemd，它仍运行在 Microsoft WSL2 内核和开发环境中。正式 G5
要求原生 Linux x86_64 或经用户批准的完整虚拟机，通过实际 `systemctl` 和 `journalctl` 场景。

因此 `tools/release/systemd_runner.py` 会把当前环境分类为 `DEVELOPMENT_ONLY`，并且在缺少十个
正式场景时绝不会生成 G5 PASS。环境分类是防止“静态 unit 校验通过”被夸大为“系统服务已经
验收”的硬边界。

### 7.4 本项目如何关闭 G5

最终 G5 没有在 WSL2 中执行，而是在 VMware Ubuntu Server 24.04 x86_64、PID 1 为 systemd 的
专用虚拟机中运行。十个场景全部 PASS，其中 broker 不可用期间串口仍成功完成 255 次请求；
broker 恢复后 MQTT 重新连接并恢复发布。重复启停完成 10 轮，fd/thread 漂移为 0。

runner 最终生成 `summary.status=PASS`、空 `failures.json`、`PASS` 标志和完整 `SHA256SUMS`。
测试结束后服务用户、组、unit、配置、进程和监听端口均被清理。这里验证的是 Linux x86_64
软件部署和生命周期，不包含树莓派、ARM64 或真实 RS485/CAN 物理层。

## 9. 常见错误和安全边界

- 不要从未提交工作区制作正式 bundle；正式证据必须绑定用户提供的候选提交。
- 不要只看最后一次 PASS；失败 run 必须保留，修复应有对应测试。
- 不要把 `systemd-analyze verify` 等同于实际服务启动验收。
- 不要把短时 smoke 代替 8 小时 G4。
- 不要把 WSL2/PT​​Y 证据写成真实 RS485/CAN 硬件结论。
- 不要把 SHA-256 写成身份签名或安全认证。
- 不要在普通测试中修改宿主机 systemd；正式安装和 `sudo` 操作需单独授权。
- 不要使用 `pkill`、`killall` 按进程名清理；只回收 runner 自己创建的进程组。
- 不要把包含主机名、私人路径、IP、序列号或凭据的原始证据提交到公开仓库。
