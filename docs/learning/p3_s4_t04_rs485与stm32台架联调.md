## 1. 本工作块解决什么问题

此前通过 PTY 验证的是 Linux 用户态串口、Modbus RTU 编解码、调度、超时、重试、数据质量和
MQTT 上行。PTY 不经过差分电气层，无法证明 USB-RS485、线缆、终端、实际从站或 STM32
收发器能够工作。

T04 的作用是把软件网关接入两类真实对端：

- TAS-WS-R00020 商用 Modbus RTU 温湿度从站，用于第三方互操作；
- NUCLEO-F446RE + Waveshare RS485 CAN Shield，用于自研从站、传感采集和可控故障；
- CANable/candleLight 作为树莓派或 Windows 的 CAN 对端，验证 Shield 的经典 CAN 链路。

## 2. 所需术语和基础概念

- **UART**：MCU 内部的异步串行控制器，输出 TX/RX 单端逻辑信号。
- **RS485**：使用 A/B 差分线传输串行比特的物理层；它不是 Modbus 协议本身。
- **Modbus RTU**：在串行链路上规定地址、功能码、数据和 CRC 的应用协议。
- **CAN**：带仲裁、帧校验、确认和错误处理的多主总线；当前 Shield 使用经典 CAN 2.0。
- **CANopen**：运行在经典 CAN 上的高层设备协议，当前项目尚未实现。
- **收发器**：把 MCU 逻辑电平转换为 RS485 或 CAN 差分电平的器件。
- **终端电阻**：位于总线两个物理端点、用于匹配传输线特性阻抗的电阻，常见为 120 Ω。
- **偏置**：在没有节点驱动 RS485 总线时提供确定空闲电平的网络，整条总线不能多处随意启用。
- **SocketCAN**：Linux 将 CAN 设备表示为 `can0` 等网络接口的统一编程接口。

## 3. 技术和协议的工作原理

### 3.1 从 UART 到 Modbus RTU

STM32 的 UART 产生字节流。Waveshare Shield 上的 MAX3485 把 TX/RX 逻辑转换为 A/B 差分
信号，并由方向控制信号决定发送或接收。Modbus RTU 再在字节流上定义：

```text
从站地址 | 功能码 | 数据 | CRC16 低字节 | CRC16 高字节
```

Linux 网关是唯一主站，同一 RS485 总线上任一时刻只能有一个在途请求。商用从站和 STM32
必须使用不同地址。

### 3.2 为什么只在两个端点放 120 Ω

长导线具有传输线特性，阻抗突变会产生反射。端点电阻吸收传播到总线尽头的能量。中间节点应以
高输入阻抗短支线并入主干；若每个节点都并接 120 Ω，总负载会过低，收发器可能无法维持规定的
差分电压。

### 3.3 CAN 与 RS485 的差异

RS485只定义电气传输，Modbus RTU负责寻址和请求/响应；CAN控制器自身已经实现仲裁、CRC、ACK、
错误计数和重发。Waveshare Shield上的SN65HVD230只负责CAN物理层，STM32F446RE的bxCAN负责
CAN数据链路层。树莓派通过CANable的candleLight固件和Linux `gs_usb`驱动获得SocketCAN接口。

## 4. 本项目中的数据流和线程角色

### 4.1 RS485/Modbus路径

```text
TAS-WS-R00020 ─┐
               ├─ RS485 A/B ─ USB-RS485 ─ 树莓派 C++ 网关 ─ MQTT Broker
STM32 自研从站 ┘
```

树莓派串口I/O线程仍是唯一串口所有者；调度器提交请求，I/O线程收发RTU帧，质量模块生成
fresh/stale/offline/invalid，MQTT线程异步发布。硬件接入不应绕过已经冻结的队列和线程边界。

### 4.2 STM32本地采集路径

```text
BME280 ─ SPI ─┐
ADXL345 ─ SPI ├─ NUCLEO-F446RE ─ 输入寄存器 ─ Modbus RTU
VEML7700 ─ I²C┘                  └─ 状态/报警帧 ─ CAN
```

BME280与ADXL345共享SPI1的SCK/MOSI/MISO，但使用独立CS；VEML7700使用另一组I²C引脚。
Waveshare Shield默认占用PB8/PB9用于CAN、PA8用于RS485方向、PA9/PA10用于RS485 UART。
传感器最终引脚必须在CubeMX中结合Morpho排针重新核对。

## 5. 关键接口和预期执行过程

当前仓库尚没有通过实物验证的STM32固件，下列内容属于待实现合同：

- STM32启动后初始化时钟、GPIO、SPI、I²C、UART、CAN、DMA和FreeRTOS；
- 采集任务更新BME280、ADXL345和VEML7700快照；
- Modbus任务把快照映射到输入/保持寄存器并响应功能码；
- CAN任务周期发送心跳、设备状态和报警；
- 诊断任务记录CRC、超时、队列、传感器和复位原因；
- 树莓派先通过商用从站建立已知可用基线，再加入STM32，避免两端共同错误造成假成功。

## 6. 为什么选择当前方案

- 商用从站提供第三方互操作证据，STM32提供可控实现和故障注入；
- F446RE资源充足，可同时学习FreeRTOS、SPI、I²C、UART、DMA和bxCAN；
- Shield把MAX3485和SN65HVD230集成到一块板上，减少初次物理层搭建难度；
- BME280、ADXL345、VEML7700覆盖环境、振动和光照，接口又能展示共享SPI与独立I²C；
- candleLight/SocketCAN使用Linux标准CAN接口，避免把核心程序绑定到只支持Windows的私有SDK。

## 7. 常见错误、失败模式和安全边界

- 把RS485等同于Modbus，或仅看到“RS485”字样就认定支持Modbus；
- A/B命名相反、串口参数不一致、从站地址重复；
- 三个节点都启用120 Ω，或总线两端均未端接；
- 把12 V接入NUCLEO、Shield或3.3 V传感器；
- 开放式AC/DC电源裸露接市电；当前MS-15-12在完成外壳、保险、接地和端子防护前不得使用；
- 把非隔离USB-RS485写成隔离部署；到货后必须以芯片、手册和结构核验；
- SPI两个设备共用CS，导致两个器件同时驱动MISO；
- 把Windows中能发送一帧CAN误写成树莓派SocketCAN和长期可靠性均已通过；
- 把短时硬件读写替代8小时软件长稳，或用PTY结果替代物理层证据。
