# P3-S5-T03｜长稳测试与资源趋势判定

## 1. 本工作块解决什么问题

普通单元测试回答“某个输入是否得到正确输出”，故障矩阵回答“单次异常能否被识别和恢复”。
长稳测试（soak test）还要回答：程序持续运行时，资源是否缓慢增长、线程是否卡住、周期故障
是否每次都恢复、证据是否足以复核。

T03 没有直接声称程序已稳定运行 8 小时，而是把 T04 和 S6 所需的 profile、runner、driver、
摘要器和机器判定规则实现出来，并用 90 秒 smoke 验证工具链。

## 2. 术语和基础概念

- warm-up：启动预热期。连接、缓存和线程刚建立时的瞬态不适合代表稳态。
- steady state：预热后负载和资源进入相对稳定的阶段。
- fault window：主动注入故障的时间窗口；恢复宽限也不进入正常性能统计。
- oracle：测试预言机，把“应该怎样”转成可执行的真假条件。
- RSS（Resident Set Size）：进程当前驻留在物理内存中的页；它不等于虚拟地址空间。
- file descriptor（fd）：进程持有的文件、socket、PTY 等内核句柄。
- percentile：分位数。P95 表示 95% 样本不大于该值，不是平均值。
- slope：随时间的变化斜率。本项目用 MiB/hour 表示 RSS 长期趋势。

## 3. 为什么不能只看峰值

峰值适合发现突然的资源爆炸，却不擅长识别每小时只增长少量的泄漏。反过来，单次 allocator
扩容会抬高 RSS，但之后长期稳定，并不等于持续泄漏。因此本项目同时看：峰值、warm-up 后
5 分钟中位数桶的线性趋势，以及首末 30 分钟稳态中位数差。

中位数能降低单个采样尖峰的影响；趋势仍只是检测信号，不是数学上证明“绝无泄漏”。若趋势
失败，应结合 ASan/LeakSanitizer、对象生命周期和重复实验定位。

## 4. P50、P95、P99 和最大值

平均值会掩盖少量严重慢请求。P50 描述典型体验，P95/P99 描述尾部延迟，最大值用于捕获最坏
观察。本项目只把 warm-up 结束后、且不在故障与恢复窗口中的成功 attempt 放入正常时延分布；
超时和故障延迟单独按错误类别判断，避免把“故障按设计发生”误算成正常性能退化。

## 5. 本项目中的进程、线程和数据流

```text
run_soak.py
├─ Mosquitto 进程
├─ mosquitto_sub 进程
├─ gateway_soak_driver 进程
│  ├─ GatewayRuntime 串口/调度线程
│  ├─ MQTT worker
│  └─ 三从站 PtyBusHarness
├─ /proc 资源采样
└─ 分段证据写入
       ↓
summarize_soak.py
├─ 正常/故障/恢复窗口切分
├─ 每个循环的触发、分类和恢复 oracle
├─ 时延、吞吐、资源趋势和队列判定
└─ summary/failures/SHA256SUMS
```

Python 管进程和证据，C++ driver 持有真实 `GatewayRuntime`、MQTT sink 和 PTY 仿真总线。网络
调用仍在 MQTT worker 内，monitor 不获取运行时锁。

## 6. 关键源码执行过程

- `tools/soak/profile.py`：解析 `extends`，校验路径、时长、故障不重叠、正式提交 ID 和
  preflight/release 语义一致性。
- `tools/soak/process.py`：每个子进程创建独立进程组；先 SIGTERM，有界等待后才 SIGKILL。
- `tools/soak/runner.py`：启动 broker/subscriber/driver，按 profile 注入 broker 故障，每 5 秒
  读取 `/proc`，分段保存日志，最后保证回收子进程。
- `tools/soak/gateway_soak_driver.cpp`：调度动态 PTY 故障、输出 heartbeat 和完整统计；顶层异常
  被转换为非零退出码，不能静默成功。
- `tools/soak/summary.py`：逐循环检查七类故障；累计计数必须单调；RSS 先形成 5 分钟中位数桶
  再计算斜率；任一强制 oracle 失败即生成 failure。
- `tools/simulation/pty_bus_harness.cpp`：测试与 soak 共用三从站 PTY 总线，支持动态 fault 和
  disconnect/reconnect。
- `src/runtime/gateway_runtime.cpp`：`request_completed` 记录 monotonic 时间与 attempt 时长。

实施 smoke 时发现一个真实边界：延迟响应到达后，解析器正确拒绝了晚帧，但运行时把这种协议
不匹配误当成串口 I/O 故障并关闭健康 PTY，导致后续恢复失败。现在只有真正的 peer/read I/O
错误才要求重开串口；晚帧被丢弃后健康串口保持打开，并有 PTY 集成回归测试保护。

## 7. 为什么选择当前方案

- 使用本地 Mosquitto 和 PTY，可在硬件到货前稳定复现软件路径；
- Python 只用标准库，减少长稳 runner 自身的依赖和失效面；
- profile 与 schema/语义 validator 分离：JSON schema 管结构，代码管跨字段约束；
- 原始日志分段且不覆盖，避免单文件无限增长；
- smoke、preflight、release 共用执行链，减少“测试工具与正式工具不是同一套”的偏差；
- 每循环判定，避免八次故障只成功一次仍被汇总为 PASS。

## 8. 常见错误、失败模式和安全边界

- 把一次 90 秒 PASS 写成“已通过 8 小时长稳”；
- 只看进程还活着，不检查 heartbeat、吞吐、队列和数据质量；
- 故障根本没触发，却因为没有错误日志而判 PASS；
- 只检查最后一个故障循环，漏掉中间偶发恢复失败；
- 只看 RSS 峰值，忽略缓慢斜率；或把一次缓存扩容直接叫作内存泄漏；
- 用 wall clock 计算持续时间，受系统校时影响；本项目用 monotonic clock；
- 让 runner 的列表或日志无界增长；
- 将 WSL/PTy 软件结论外推为真实 RS485 电气可靠性。

原始证据可能很大，应保留在 `artifacts/soak/`，只把去敏摘要写入文档。runner 不执行 Git；
正式 source revision 必须由项目所有者确认。

## 10. 后续学习资料

以下均为一手资料，访问日期为 2026-08-12：

- [Linux Kernel：The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)：理解
  `/proc/<pid>/status`、RSS、线程和 fd 观测。
- [Python 3.12：subprocess](https://docs.python.org/3.12/library/subprocess.html)：理解子进程、
  pipe、超时和返回码。
- [Python 3.12：signal](https://docs.python.org/3.12/library/signal.html)：理解 SIGTERM 与信号
  处理边界。
- [CMake：ctest(1)](https://cmake.org/cmake/help/latest/manual/ctest.1.html)：理解 CTest 退出码、
  timeout、label 和重复执行。
- [Clang：AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html)：理解越界、
  use-after-free 和泄漏检测边界。
- [Clang：ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html)：理解数据竞争检测、
  运行时开销和平台限制。

阅读这些资料时应记住：Sanitizer PASS 不能代替长稳，长稳 PASS 也不能证明所有线程交错都已
覆盖；两者解决的是不同风险。
