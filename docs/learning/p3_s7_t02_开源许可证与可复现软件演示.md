# P3-S7-T02 教程：开源许可证与可复现软件演示

> 对应工作块：P3-S7-T02  
> 文档状态：已审核固化，内容对应当前真实实现  
> 适用范围：Industrial-IOT-Gateway Linux x86_64 软件 MVP  
> 编制日期：2026-08-13

## 1. 本工作块解决什么问题

P3-S7-T02 没有增加新的 Modbus 或 MQTT 业务能力，而是解决“软件已经能运行，但还不能作为
清楚、可信、容易复现的开源候选项目交付”的问题。

本工作块补齐了三件事：

1. 用 `LICENSE` 明确项目自有代码采用 MIT License；
2. 用 `THIRD_PARTY_NOTICES.md` 说明第三方软件仍受各自许可证约束；
3. 用 `tools/demo.py --profile pty-mqtt` 把配置、构建和一个真实 PTY+MQTT 集成场景压缩为
   一条公开命令。

它在项目中的角色可以概括为：把“开发者本机上验证过的工程”转换为“他人可以理解授权边界、
执行固定命令并得到明确退出结果的软件候选交付物”。

## 2. 基础术语

### 2.1 开源许可证（open-source license）

许可证不是“代码介绍”，而是版权持有人授予他人的法律许可。没有许可证的公开仓库并不等于
任何人都可以自由复制、修改和分发。

本项目采用 MIT License。它的核心结构是：

- 允许使用、复制、修改、合并、发布、分发、再许可和销售；
- 要求在软件的重要副本中保留版权声明和许可文本；
- 软件按现状提供，作者不作担保并限制责任。

项目中的标准版权行是：

```text
Copyright (c) 2026 fengchechecheche
```

本教程解释工程实现，不构成法律意见。

### 2.2 第三方声明（third-party notice）

项目许可证只覆盖项目作者有权许可的自有代码。yaml-cpp、Paho 和 nlohmann/json 不会因为被
本项目使用，就自动改成 MIT License。

`THIRD_PARTY_NOTICES.md` 的作用是告诉接收者：

- 使用了哪些第三方组件；
- 使用的是哪个固定版本；
- 它在编译、运行或测试中的角色；
- 它是否被复制进项目安装包；
- 去哪里查看对应许可证和版权文本。

### 2.3 可复现演示（reproducible demo）

“演示”不是打印一行 `PASS`，而是执行真实程序路径并把失败传播给调用者。当前 demo 会：

1. 运行 CMake configure；
2. 构建真实 MQTT+PTY 集成测试目标；
3. 启动回环 Mosquitto 和三从站 PTY 总线；
4. 运行串口轮询和 MQTT 发布；
5. 停止 broker，验证串口采集仍继续；
6. 恢复 broker，验证 MQTT 重连；
7. 有界停止并回收进程；
8. 只有所有步骤通过才返回 0。

## 3. 为什么 LICENSE 与 NOTICE 不能合并

可以把软件交付想成两个并行的授权层：

```text
项目自有源码 ── LICENSE（MIT）

第三方组件 ─── THIRD_PARTY_NOTICES.md
               ├── yaml-cpp 自己的许可证
               ├── Paho 自己的许可证
               ├── nlohmann/json 自己的许可证
               └── 测试工具自己的许可证
```

如果只放项目 MIT 文本，接收者可能误以为所有第三方代码也由项目作者按 MIT 重新授权。反过来，
如果只列第三方依赖而没有项目 LICENSE，接收者仍不知道项目作者允许怎样使用自有代码。

因此当前仓库采用四层文件：

- `LICENSE`：项目自有代码授权；
- `THIRD_PARTY_NOTICES.md`：Release 接收者需要看到的第三方声明；
- `docs/third_party_inventory.md`：工程维护者使用的详细依赖盘点；
- `README.md`：给使用者的入口、范围和链接。

## 4. 第三方组件的交付层级

### 4.1 头文件代码编译进入目标

nlohmann/json 是典型 header-only（仅头文件）依赖。编译器会把使用到的模板和内联实现编译进
MQTT 目标，因此即使 Release 包里没有单独的 `libnlohmann_json.so`，也要保留其版权和
MIT/Expat 声明。

### 4.2 动态链接的系统包

yaml-cpp、Paho C++、Paho C 和 glibc 由 Ubuntu 包管理器安装，`gateway_app` 在运行时动态
加载对应共享库。本项目当前安装树不复制这些 `.so`，因此 NOTICE 清楚写明“系统包提供、共享库
不随本项目安装包分发”。

如果未来把 `.so` 一并装进压缩包，这个结论就失效，必须按实际文件重新生成依赖和许可证清单。

### 4.3 测试专用依赖

GoogleTest 用于编译测试目标；Mosquitto 用作本地回环 broker。它们不进入 `gateway_app` 的
运行安装树，但仍应出现在开发依赖清单中，避免把测试环境误认为“无外部依赖”。

### 4.4 构建工具

CMake、Ninja、GCC/Clang 和 CTest 是构建或检查工具。使用某个工具编译项目，并不等于把该
工具链接或捆绑进 `gateway_app`。因此 inventory 把它们与运行时依赖分开。

## 5. CMake 的 configure、build、test 与 install

初学者容易把四个阶段混在一起：

```text
configure → build → test → install staging
```

### 5.1 configure

```bash
cmake -S . -B build/demo-pty-mqtt ...
```

CMake 在这个阶段检查编译器、依赖、`pty.h` 和选项，并生成 Ninja/Make 构建规则。configure
成功不代表代码已经编译或测试通过。

### 5.2 build

```bash
cmake --build build/demo-pty-mqtt \
  --target gateway_mqtt_pty_runtime_integration_test
```

build 把源码编译、链接为真实测试可执行文件。T02 demo 只构建所需目标，避免让快速演示承担
全量质量门的耗时。

### 5.3 test

```bash
ctest --test-dir build/demo-pty-mqtt --output-on-failure \
  --no-tests=error \
  -R '^MqttPtyRuntimeIntegrationTest\.SerialPollingContinuesWhileBrokerIsUnavailable$'
```

`--no-tests=error` 很重要：如果正则写错并匹配到 0 项，CTest 必须失败，不能制造“没有执行任何
测试但返回成功”的假演示。

### 5.4 install staging

```bash
DESTDIR=/tmp/stage cmake --install build/release
```

install 把二进制、systemd unit、配置、LICENSE、NOTICE 和文档放入模拟的目标文件系统。使用
`DESTDIR` 可以在不污染 `/usr/local` 的情况下检查包内容。

## 6. demo.py 的实现路径

### 6.1 参数解析

脚本用 Python `argparse` 只接受：

```text
--profile pty-mqtt
--build-dir build/...   # 可选，且必须留在仓库 build/ 下
--jobs 1..64            # 可选
```

未知 profile 由 argparse 返回 2。build 目录不能通过 `../` 逃出仓库 `build/`，降低误写其他
目录的风险。

### 6.2 平台门

脚本主动检查：

- 操作系统必须是 Linux；
- 架构必须是 `x86_64` 或 `amd64`；
- `cmake`、`ctest`、`c++` 和 `mosquitto` 必须可用。

因此在 ARM64 上运行不会产生似是而非的 x86_64 PASS，而是返回“环境不支持”。这不是说代码
永远不能支持 ARM64，只是说明当前版本没有相应验收证据。

### 6.3 命令执行

脚本把命令保存为参数数组，并使用 `shell=False`：

```python
["cmake", "-S", str(repository_root), "-B", str(build_dir), ...]
```

与拼接 shell 字符串相比，这能减少空格、引号和命令注入问题，也让单元测试能精确检查每个
参数。

### 6.4 返回码传播

| 返回码 | 含义 |
|---:|---|
| 0 | configure、build 和真实集成测试全部通过 |
| 2 | 参数、jobs 或 build 目录非法 |
| 3 | 操作系统、架构或依赖不满足 |
| 4 | 配置、构建、测试或进程启动失败 |
| 5 | 超时、中断或清理失败 |

上层脚本和 CI 可以只检查返回码，不需要从中文输出中猜测成功与否。

## 7. 进程组、超时与清理

### 7.1 为什么创建新会话

外部命令使用 `start_new_session=True`。子命令及其后代进入独立进程组后，超时时可以向整个
组发送信号，而不是只杀死最外层 CMake/CTest 进程、留下 broker 或测试进程。

### 7.2 关闭顺序

```text
达到超时或 Ctrl+C
  → 向本次进程组发送 SIGTERM
  → 等待短暂宽限期
  → 仍未退出才发送 SIGKILL
  → 回收子进程状态
```

SIGTERM 给程序执行析构、flush 和有界停止的机会；SIGKILL 是最后兜底，程序不能捕获它。

脚本禁止使用 `pkill mosquitto` 或 `killall`，因为那会按名字误杀用户自己启动的 broker。当前
集成测试中的 broker 对象也只保存和终止自己创建的 PID。

## 8. 一键 demo 为什么不等于完整验收

demo 的目标是几分钟内回答：“这个源码树能否在支持环境中编译并跑通一条有代表性的 PTY +
MQTT 软件链路？”它不能回答：

- 8 小时内资源是否稳定；
- 全部 15 个故障场景是否通过；
- systemd 在原生 Linux 上是否正确重启和停止；
- Raspberry Pi/ARM64 能否构建和运行；
- USB-RS485 的 A/B/GND、终端、隔离和共模范围是否正确；
- STM32、CAN 或真实传感器是否已经联调；
- 生产 MQTT TLS、凭据和日志保留策略是否合格。

所以脚本无论成功还是失败都会先输出：

```text
DEMO_SCOPE=Linux_x86_64_PTY_MQTT_software_only
HARDWARE_VALIDATED=false
```

这是把证据边界写进机器输出，而不是只靠读者记住 README 的免责声明。

## 9. 常见错误与安全边界

### 9.1 “公开仓库就自动是开源”

错误。公开可读和获得复制/修改/分发许可不是同一件事。应提供清楚的 LICENSE。

### 9.2 “项目是 MIT，所以依赖也都是 MIT”

错误。每个依赖保留自己的许可条件，项目 NOTICE 只记录和传递这些边界。

### 9.3 “CTest 返回 0 就说明测试通过”

如果测试正则匹配 0 项且没有 `--no-tests=error`，可能产生误导。本项目把 0 项测试视为失败。

### 9.4 “为了清理方便可以 pkill”

错误。演示脚本只能停止自己创建的进程组，不能影响同机用户已有服务。

### 9.5 “PTY 演示通过就说明 RS485 没问题”

错误。PTY 只模拟字节流和软件时序，不包含差分电压、终端电阻、接地、隔离、EMC 或收发器方向
控制。
