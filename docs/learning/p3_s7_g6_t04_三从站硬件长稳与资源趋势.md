# P3-S7-G6-T04：三从站硬件长稳与资源趋势

> 文档性质：中文教学文档
>
> 对应实现：候选提交 `c5ddc365ae46c920a78d71ef67ee13fe9de39651`
>
> 当前事实：3600 秒预跑和 28800 秒正式真实硬件长稳均 PASS；G6-T05 尚未关闭
>
> 适用环境：C++17、Linux ARM64、systemd、Modbus RTU 19200 8E1、MQTT 3.1.1

## 1. 本工作块解决什么问题

短时测试能证明程序“现在能跑”，却很难发现只在数小时后出现的问题，例如：内存缓慢增长、文件
描述符泄漏、线程越积越多、某个从站偶发饥饿、MQTT 队列持续堆积、日志填满磁盘，或树莓派因
温度和供电问题发生降频。

T04 的作用是让项目三完整的数据链路在真实三从站台架上持续工作，并用可自动判定的证据回答：

```text
真实传感器持续响应吗？
每个从站都能公平获得轮询机会吗？
MQTT 上行会阻塞串口采集吗？
资源使用是稳定波动，还是随时间持续增长？
树莓派是否发生过热、欠压或降频？
遇到偶发超时后，重试是否真正闭环？
运行结束后，证据是否完整且服务是否恢复？
```

本工作块不是为了增加业务功能，而是验证当前组合在冻结负载下的持续运行能力。

## 2. 所需术语和基础概念

- **长稳测试（soak test）**：让系统在接近目标负载下持续运行较长时间，观察功能、资源和恢复
  是否随时间退化。
- **预跑（preflight）**：在昂贵的正式长稳前，用较短但合同一致的运行发现环境和工具问题。
- **正常窗口（normal window）**：排除启动预热和受控收尾后的主要判定时间段。
- **测试预言机（test oracle）**：将观测值与冻结门限比较并自动输出 PASS/FAIL 的规则。
- **逻辑请求（logical request）**：对上层而言的一次读取任务；它可能包含第一次尝试和后续重试。
- **尝试（attempt）**：逻辑请求中的一次物理 Modbus 发送与响应等待。
- **最大成功间隔（maximum success gap）**：同一从站相邻成功请求之间的最大时间，用于发现饥饿。
- **高水位（high-water mark）**：队列在整个运行期间达到过的最大占用量。
- **RSS（resident set size）**：进程当前驻留在物理内存中的页面规模。
- **资源漂移（resource drift）**：fd、线程或内存基线随运行时间持续变化的现象。
- **throttled 状态**：树莓派固件记录的欠压、限频、降频及历史状态位。
- **原始证据（raw evidence）**：未经聚合的逐事件日志、MQTT 消息和资源样本。
- **派生证据（derived evidence）**：从原始证据计算出的摘要、CSV、趋势和 oracle。

## 3. 为什么先跑一小时，再跑八小时

八小时测试成本高。如果串口路径、权限、profile 或证据目录在启动后几秒就出错，直接等待八小时
没有意义。一小时预跑用与正式运行相同的候选、真实硬件、systemd 服务和判定逻辑，先检查：

1. 三个从站与 MQTT 是否持续有数据；
2. runner 是否有权限读取 `/proc/<MainPID>` 和 journal；
3. 日志分段、心跳、容量和 SHA-256 是否正常；
4. 结束后能否恢复证据所有权和服务；
5. 资源增长速度是否存在明显异常。

预跑 PASS 只代表“具备启动正式长稳的条件”。正式八小时必须使用新的 run ID 和独立证据目录，
不能把一小时和七小时拼起来，也不能把预跑结果代替正式结论。

## 4. 本项目中的数据流和线程角色

```text
PollScheduler
  ↓ 产生地址 1/2/4 的周期请求
有界 request queue
  ↓
GatewayRuntime 串口执行路径（唯一串口所有者）
  ↓ Modbus RTU 请求、响应、CRC、超时与重试
事件与新鲜度处理
  ├── 结构化 journal
  └── PublishSink
        └── MqttPublishSink（独立网络活动 + 有界缓存）

systemd
  └── 管理网关进程生命周期、MainPID 和 NRestarts

g6_t04_runner.py（进程外观察者）
  ├── journal collector
  ├── MQTT subscriber
  ├── resource sampler
  ├── heartbeat
  └── evidence finalizer
```

关键边界是：T04 runner 只观察和管理证据，不替代网关，不启动 PTY 从站，也不注入故障。它从
systemd 取得真实 MainPID，订阅本次运行的 MQTT，并读取当前 invocation 的结构化 journal。

## 5. 关键源码与真实执行过程

### 5.1 profile 和输入合同

正式实现使用：

```text
config/hardware/g6_t04_preflight_profile.json
config/hardware/g6_t04_release_profile.json
tools/hardware/g6_t04_contract.py
tools/hardware/g6_t04_runner.py
```

`g6_t04_contract.py` 中的 `load_profile()` 和 `validate_profile()` 负责拒绝缺字段、错误时长或不一致
门限；`validate_source_revision()` 要求完整 40 位提交，避免把未固定工作区作为正式证据。

### 5.2 证据采集与分段

`g6_t04_runner.py` 的 `EvidenceStore` 管理原始文件、分段 writer、派生文件和哈希。运行期间：

1. `run()` 读取 profile 并冻结 run ID、候选提交和起始单调时间；
2. journal collector 只采集当前网关 invocation 的事件；
3. MQTT subscriber 捕获 `industrial_iot_gateway/#`，再按 run ID 和消息字段过滤；
4. 资源采样器每 5 秒读取进程、systemd、温度、throttled、磁盘和 boot ID；
5. 每 5 秒追加 `heartbeats.jsonl`，并记录当前证据字节数；
6. 大文件通过 `RotatingTextWriter` 按确定性编号轮转；
7. 运行结束后读取全部分段，生成 summary、failures、派生 CSV 和 SHA256SUMS；
8. PASS/FAIL 标记只在最终判定完成后生成。

原始文件不因生成 CSV 而删除。这样发现问题时可以沿着时间戳从资源峰值追到请求、MQTT 消息和
systemd 状态，而不是只剩一张无法复算的曲线图。

### 5.3 自动判定

`g6_t04_contract.py` 的 `build_indices()` 建立事件索引，`evaluate_run()` 负责聚合并输出 oracle。
主要计算包括：

- 正常窗口内各从站的逻辑请求成功率；
- 同一从站相邻成功请求的最大间隔；
- 21 个冻结任务的覆盖率；
- MQTT sequence 重复、倒退和 run ID 混入；
- publish failure、队列高水位、drop 和 drain；
- RSS 峰值、斜率和稳态差值；
- CPU 平均值与 P95、fd/thread 峰值和漂移；
- 温度、throttled、boot ID、磁盘和证据容量；
- SIGTERM 关闭时间及意外退出。

`hardware_long_soak_pass=true` 只有在 `profile_kind=release` 且全部强制 oracle PASS 时才能出现。

## 6. 为什么成功率要按逻辑请求计算

八小时运行中 TAS-A 有两次第一次尝试超时，随后第二次尝试成功。如果只统计物理尝试，成功率会
略低于 100%；如果只看最终成功，又可能把频繁超时掩盖掉。因此项目同时保留两层统计：

```text
尝试层：暴露线路、响应时间和重试频度
逻辑请求层：判断上层轮询任务最终是否取得数据
```

本次请求 41608 和 109939 的第一次尝试都在约 701 ms 记录超时，隔离完成后分别在约 65 ms 和
72 ms 成功。两次异常都保留在原始证据中；地址 1 的最终逻辑请求为 14100/14100 成功。

这类分层能避免两个极端：既不会因为一次可恢复尝试失败而误判整个任务失败，也不会用最终成功率
掩盖真实总线质量下降。

## 7. 为什么最大成功间隔比平均成功率更重要

假设一个从站前 30 分钟连续成功、后 30 分钟完全饿死，整体成功率仍可能看起来不错。平均值不能
描述“最长多久没有服务”。最大成功间隔直接约束最坏等待时间：

```text
TAS-A：4.886 s
TAS-B：4.895 s
STM32：2.997 s
冻结门限：<= 10 s
```

它和成功率组合后，才能同时发现“多数请求失败”和“少量设备长期得不到调度”两类问题。

## 8. 如何理解资源趋势

### 8.1 RSS 峰值、斜率和稳态差值

只看 RSS 峰值无法区分正常启动分配与内存泄漏。T04 同时观察：

- 峰值：有没有超过绝对容量门限；
- 斜率：RSS 是否随时间近似单调增长；
- 稳态差值：稳定窗口末尾是否明显高于开头。

本次 RSS 峰值约 6.77 MiB，斜率约 `0.000005 MiB/h`，稳态差值约 0.027 MiB，没有显示持续泄漏。
但一次八小时低斜率不是数学意义上的“永不泄漏”，它只证明当前候选、负载和时间范围内没有可观测
的失控趋势。

### 8.2 fd 和线程漂移

网络重连、日志文件轮转或串口重开如果只创建不释放，会造成 fd 或线程缓慢增加。本次 fd 最大值为
5、漂移为 0；线程最大值为 7、漂移为 0。这比只在运行末尾执行一次 `ps` 更有说服力，因为 5 秒
资源样本覆盖了整个运行。

### 8.3 CPU 平均值和 P95

平均 CPU 会隐藏短时尖峰，最大值又容易被一次采样噪声影响。P95 表示 95% 样本不高于该值，适合
描述长期常见上界。本次平均约 1.91%，P95 约 2.20%，没有任何累计超过 90% 的时间。

### 8.4 温度与 throttled

温度说明当前热状态，`get_throttled` 同时包含当前位和历史位。正式判定要求：

- SoC 温度始终低于 80℃；
- 当前欠压、限频、降频相关位始终为 0；
- 历史位 16～19 不得相对启动基线新增。

本次最高温度 62.8℃，当前位和新增历史位均为 0。历史位采用“相对基线新增”而非简单要求整个
机器历史永远为 0，是为了区分本次运行造成的问题和更早的主机历史。

## 9. MQTT stale 消息应如何解读

`stale` 表示某项测量超过新鲜度门限，并不等同于 MQTT 的 RETAIN 标志，也不自动等同于设备永久
离线。完整原始捕获中出现 16 条 stale：BME280 温度 9 条、RS485 错误计数 7 条，最终均恢复 fresh。

分析 stale 时至少要一起检查：

1. 对应设备的 Modbus 最大成功间隔是否越界；
2. 是否存在连续逻辑请求失败；
3. MQTT sequence 是否重复或倒退；
4. 是否出现 publish failure、drop 或队列溢出；
5. 末态是否恢复 fresh。

本次上述硬门均通过，因此 stale 被保留为短暂质量转换，而不是删除后再宣称“全程没有异常”。

## 10. 为什么证据也需要容量与完整性门

长稳测试如果无限写日志，测试工具本身可能填满磁盘并破坏被测系统；如果只保留摘要，又无法复盘。
本项目采用折中方案：

```text
逐事件原始数据 + 64 MiB 分段
5 秒资源样本和心跳
派生 CSV/summary/index
总证据上限 10 GiB
每个正式文件写入 SHA256SUMS
```

本次收尾后证据约 860.5 MB，远低于 10 GiB。SHA-256 验证的是文件在固化后没有发生无声变化；它
不能证明测试设计本身正确，所以仍需同时审查 profile、oracle 和候选提交。

## 11. 为什么 runner 需要 sudo，而网关仍使用独立用户

正式网关由 systemd 以独立用户 `iot-gw` 运行，而 runner 需要读取另一个用户进程的
`/proc/<MainPID>/fd`、状态和资源信息。Linux 对跨用户 `/proc` 访问有权限限制，普通 `iot-rp`
运行第一轮 smoke 时因此得到 `PermissionError`。

解决方式是只让正式 runner 在受控时段以 sudo 执行读取和证据收尾，而不是把网关改回登录用户或
永久放宽服务权限。结束后证据所有权恢复为 `iot-rp:iot-rp`，网关继续由 `iot-gw` 运行。这样保留了
systemd 的最小权限边界，也满足完整观测需求。

## 12. 为什么选择当前方案

- 使用真实 systemd 服务，而不是测试进程，覆盖真实用户、unit、journal 和生命周期；
- 用单调时间计算时长、响应和间隔，避免系统时钟校准影响；
- 成功率与最大成功间隔并用，同时约束可靠性和公平性；
- 尝试层与逻辑请求层分开，既保留异常又正确评价重试结果；
- 原始、索引、派生三层证据兼顾复盘、自动判定和展示；
- 预跑和正式运行使用不同 run ID，避免拼接证据；
- 运行后检查进程残留、服务状态、NRestarts 和所有权，确保测试工具本身完成清理。

## 13. 常见错误、失败模式和安全边界

- 只看最后一条日志就宣布八小时 PASS；
- 在运行中放宽成功率、时长或公平性门限；
- 把重试后的成功写成“从未超时”；
- 用平均成功率掩盖单个从站长时间饥饿；
- 把 MQTT `stale` 与 MQTT RETAIN 混为一谈；
- 只保留图表，删除原始 JSONL；
- 忽略 runner/collector/订阅器残留；
- 把 PTY、短线桌面台架或八小时结果外推到长距离工业现场；
- 把持续更新趋势写成传感器计量精度认证；
- 在没有新版本发布流程时修改既有 v0.1.0 的不可变 manifest。
