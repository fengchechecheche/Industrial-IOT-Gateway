# P3-S7-G6-T05：验收证据与声明边界

> 文档性质：中文教学文档
>
> 当前事实：T00～T05 已通过；G6 已按发布后真实硬件补充验证边界关闭

## 1. 本工作块解决什么问题

一个项目“测试通过”之后，仍可能因为表述不准确而失去可信度。例如把桌面短线写成工业现场、把
一次重试成功写成从未超时、把项目五 CAN 结果写成项目三能力，或直接修改旧 Release 的硬件状态。

T05 解决的是证据治理问题：让每句话都能回答“由哪次运行、哪个提交、哪份报告证明，适用于什么
渠道，还有哪些不能外推的条件”。

## 2. 基础概念

- **事实（fact）**：源码或正式测试直接支持的客观描述；
- **声明（claim）**：从事实提炼、准备放入简历、面试或项目介绍的句子；
- **可追溯矩阵（traceability matrix）**：把验收门、判据、证据和状态逐行关联；
- **限定词（qualifier）**：限定平台、拓扑、时长和测试条件的必要文字；
- **禁止表述（prohibited wording）**：证据不足或容易误导的表达；
- **历史事实（historical fact）**：在过去阶段成立，后来由新证据解决，但不能删除的记录；
- **不可变 Release（immutable release）**：一旦形成，资产和 manifest 不因后续测试被原地改写。

## 3. 从工程事件到公开表述

```text
原始证据
  ↓ summary / failures / SHA256SUMS
验收报告
  ↓ 提取 fact，并记录限制
claim ledger
  ↓ 渠道与限定词审查
简历、面试、作品集候选
```

每一层都只能减少信息、增加限定，不能凭空增加能力。例如 T04 原始日志显示两次 TAS-A 首次尝试
超时，summary 又证明重试后逻辑请求成功。正确 claim 是“重试闭环且八小时逻辑成功率 100%”，
而不是“八小时从未发生超时”。

## 4. 为什么项目五证据可以复用但不能替代 G6

项目五已经验证 NUCLEO、Shield、三种板载传感器、默认固件和部分 RS485/CAN 路径。重复执行相同
到货验收没有价值，因此 T00 可以引用这些事实。

但项目三新增了两只 TAS、三从站共享总线、MQTT、网关进程、systemd 故障恢复和八小时组合负载。
这些新关系必须由 T01～T04 的新证据证明。证据复用遵循：

```text
复用已冻结的单体能力
≠ 复用未测试的新系统组合结论
```

## 5. 为什么历史限制不能删除

旧事实 `P3-F014` 曾记录真实硬件尚未执行。现在 G6 已补齐 RS485/商用从站/STM32 路径，但删除
旧事实会让读者误以为项目从一开始就具备硬件证据，也破坏旧简历和旧 Release 的可解释性。

正确方法是保留原 ID、增加有效期和 `resolved_by`，再追加新事实。CAN 仍未成为项目三 G6 能力，
因此“RS485 和 CAN 全部通过”仍然必须拒绝。

## 6. 为什么 G6 PASS 不能回写 v0.1.0

v0.1.0 的包、哈希、release index 和 `hardware_validated=false` 描述的是当时形成 Release 时的事实。
后续测试虽然提高了项目当前证据水平，却不能改变过去资产的内容，否则原 SHA-256 和审计链会失效。

后续有两种合规方式：

1. 把 G6 写成“v0.1.0 发布后的硬件补充验证”；
2. 若要在资产中声明硬件验证，创建新版本并重新构建、验收和索引。

## 7. 本项目新增的三类硬件 claim

### 7.1 三从站集成

必须包含 Raspberry Pi 4B、桌面短线、USB-RS485、两只 TAS、STM32 和本地 Mosquitto 等边界。
它证明三个地址和 21 个任务可以共同工作，不证明工业长线。

### 7.2 故障隔离与 systemd

17 个场景包含 TAS 支路、STM32 RESET、broker、USB-RS485、SIGTERM 和受控 reboot。可以声明
非目标从站公平性和自动恢复通过，不能扩展成电气破坏、短路、过压或 CAN bus-off。

### 7.3 八小时真实硬件长稳

可以声明三个从站正常窗口逻辑成功率均为 1.000，MQTT/资源/温度/关闭门通过。必须保留“单次
正式运行、当前桌面短线拓扑”的限定，不能使用“工业级”或“无限期可靠”。

## 8. YAML 与 CSV 为什么要同时维护

YAML 适合保存嵌套事实、限制、渠道和贡献边界，是权威台账；CSV 把每条 claim 压平成一行，便于
筛选、对照和批量检查。两者必须具有相同 claim ID、状态和事实来源。

如果 CSV 多出一条或 statement 不一致，说明投影过程失真。T05 因此同时检查：

```text
YAML claim 数 = CSV 数据行数
claim ID 唯一
source_fact_ids 均存在
公开 claim 至少有一个 evidence_refs
```

## 9. 常见错误和安全边界

- 用后续 G6 结果覆盖旧 Release manifest；
- 删除过去的 NOT_RUN 事实；
- 只看 summary PASS，删除原始异常；
- 把项目五 CAN 结果拼到项目三；
- 把温湿度“合理变化”写成计量认证；
- 在公开文档写入 IP、用户名、设备序列号或私人路径；
- 把自动化测试数量写成第三方认证；
- 未经授权直接更新正式 CV、作品集或远程 Release。

## 10. 完成与未完成的能力

完成：T00～T04 证据汇总、真实硬件事实追加、claim/CSV 追踪和不可变 Release 边界。

未完成：T05 审核与正式同步、新硬件补充版本、正式 CV/作品集更新、项目三 CAN 下游功能、计量与
工业现场验证。
