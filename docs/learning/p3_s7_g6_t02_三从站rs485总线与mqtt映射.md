# P3-S7-G6-T02：三从站 RS485 总线与 MQTT 映射

> 文档性质：中文教学正式维护版
>
> 对应工作块：P3-S7-G6-T02
> 当前边界：候选提交 `b35a01e25c95fb427fbfa165c4e7f3b030f73b8d` 的 ARM64 构建、正常基线及 TAS-A/TAS-B 对称支路故障均已通过；G6-T03/T04 尚未执行

## 1. 本工作块解决什么问题

本工作块把两只商用温湿度传感器和一块 STM32 从站接到同一条 RS485 总线上，再由树莓派上的
项目三网关依次读取数据、生成 JSONL，并向 MQTT broker 发布。它验证的不是某个从站能否单独
通信，而是多个真实从站共享一条半双工总线时，地址、时序、调度和上行映射能否同时成立。

## 2. 关键术语

- **总线（bus）**：多个设备共享的一对 RS485 A/B 差分信号线。
- **主站（master）**：主动发起 Modbus RTU 请求的设备，本项目中是树莓派网关。
- **从站（slave）**：只在收到自身地址请求后应答的设备，地址分别为1、2和4。
- **请求起始间隔（minimum request start interval）**：相邻两次主站事务开始时刻之间的最小距离。
- **轮询周期（poll period）**：某个寄存器任务计划多久执行一次。
- **供给负载（offered load）**：所有轮询任务每秒计划产生的请求数之和。

## 3. 为什么地址不同还会互相影响

地址只决定哪个从站应答，不能为每个设备创造独立带宽。三个从站仍共享同一条半双工总线，任意
时刻只能有一个事务占用线路。如果主站连续快速发帧，即使地址轮换正确，处理较慢的商用传感器也
可能尚未完成内部状态恢复，从而不应答或晚应答。

本项目的探索性运行正好说明了这一点：STM32能够承受快速请求并持续成功，但两只 TAS 大量超时。
将所有请求统一限制为至少间隔200ms后，三个地址同时恢复为全成功。因此问题在总线级时序，而非
TAS 地址冲突。

## 4. 全局限速和轮询周期为何必须同时调整

只增加200ms全局限速，最多只能让总线每秒开始5个请求。如果21个任务仍按原周期合计产生约
21.7次/秒，生产速度会长期大于消费速度，请求队列仍会持续积压，最终导致过期、合并或公平性
异常。

当前候选配置采用：

```text
TAS：4个任务 / 4秒 = 1.00次/秒
STM32：17个任务 / 6秒 ≈ 2.83次/秒
合计：约3.83次/秒
总线容量：1000ms / 200ms = 5次/秒
```

这样保留约23%的平均容量余量。全局限速解决设备最小处理间隔，较慢的轮询周期解决长期队列稳定
性，两者缺一不可。

## 5. 本项目中的执行路径

1. YAML 解析器读取 `minimum_request_interval_ms`、从站和寄存器任务；
2. 调度线程根据各任务周期产生请求；
3. 有界请求队列保存待执行请求；
4. 串口线程是唯一的 RS485 串口所有者；
5. 串口线程在发起新事务前等待全局最小起始间隔；
6. 收到响应后执行 CRC、地址、功能码和寄存器数量校验；
7. 解码线程应用数据类型、缩放和新鲜度规则；
8. JSONL sink 或 MQTT sink 根据 `device_name` 和 `register_name` 输出消息。

等待过程每10ms检查一次关闭请求，因此不会用一次不可中断的200ms休眠破坏5秒关闭预算。未配置
该字段的 PTY 和软件默认配置保持0ms，避免改变既有测试合同。

## 6. 三个设备如何映射到 MQTT

设备名固定为：

```text
tas_env_01
tas_env_02
stm32_condition_node
```

遥测 topic 形式为：

```text
industrial_iot_gateway/devices/{device_name}/registers/{register_name}
```

例如两只相同型号 TAS 的温度仍会发布到不同 topic。物理地址负责 Modbus 总线寻址，`device_name`
负责应用层身份；两者必须一一对应，不能只靠温度数值推断来源。

## 7. 常见错误和安全边界

- 只确认三个地址都能单独读取，却没有测试共总线调度；
- 把响应超时从500ms随意放宽，用更长等待掩盖过高请求频率；
- 只做发帧限速，不降低轮询任务的长期供给负载；
- 把一次原始帧成功当成 JSONL、MQTT 或 systemd 已通过；
- 在未提交工作区上生成正式证据，导致运行结果无法复现；
- 将桌面短线结果外推为长距离工业现场布线能力；
- 在本项目中执行未规划的 Modbus 写寄存器或 CAN 主动测试。

## 8. 从 `serial_io_transient` 到调度停滞：反馈闭环为什么重要

串口线程负责执行事务，调度线程负责决定当前请求是成功、重试还是终止。两者之间使用有界反馈
队列传递“尝试已经发出”和“尝试已经完成”两类消息。该反馈不是普通日志：只有调度线程消费
反馈并完成状态转换后，当前 `in-flight` 请求才会释放，下一项任务才有机会派发。

旧实现存在三类相互关联的薄弱点：

1. 串口线程使用非阻塞 `try_push` 提交反馈，却忽略返回值；
2. 调度线程调用 `mark_attempt_sent` 和 `record_attempt_result` 后，没有检查状态转换错误；
3. 运行时没有调用调度器已有的 `on_time_advanced()`，因此反馈一旦丢失或未被接受，缺少最后的
   截止时间恢复路径。

如果当前请求一直保持 `in-flight`，其 `next_wake_time` 又已经落在过去，调度循环会反复立即醒来，
表现为进程仍存活、CPU持续占用、MQTT线程继续工作，但不再产生串口请求。TAS-A支路断开实验
观察到的现象与这条失效链一致。旧证据没有记录反馈队列投递状态和调度转换错误，因此不能反推
当时究竟是一次队列投递失败，还是一次未被处理的状态转换错误；文档不把其中任一项写成已直接
观测的唯一触发点。

当前最小修复采用三层防线：

- 反馈改为最多等待100ms的有界 `push_until`；非关闭阶段投递失败时记录关键事件并进入有界致命
  停止，禁止静默继续；
- 检查每次调度状态转换，拒绝结果会记录错误类别、请求ID和尝试次数并停止；
- 当请求超过调度截止时间、晚响应隔离窗口、最大晚帧传输时间及50ms调度抖动余量后仍未闭环，
  调度线程调用 `on_time_advanced()`，把它推进为重试或终态，而不是持续空转。

`gateway_summary` 同步增加反馈投递失败、状态转换错误、截止时间恢复次数和反馈队列高水位。
其中 `requests_failed` 统计的是完成重试策略后的**终态失败**，而单次超时或
`serial_io_transient` 属于**尝试级结果**；两者不能直接按条数比较。

新增 PTY 测试连续执行24次零停机串口断开/重连，并要求每轮之后三个从站都继续取得成功请求，
同时验证反馈投递失败、状态转换错误和队列满均为0。它验证修复后的进度不变量，但不能替代真实
TAS支路拔插复验。

### 8.1 为什么“已放入串口队列”仍不等于“已经发送”

第一次修复后的真实 TAS-A 复验进一步暴露了一个更细的时间窗口。调度线程把重试对象放进有界
请求队列，只能说明串口线程未来会处理它；串口线程还可能因为全局200ms最小请求间隔而等待。
因此请求同时存在三个不同时间点：

```text
调度器入队时间 → 串口线程取出时间 → 实际开始发送时间
```

旧逻辑在请求仍处于 `queued` 时允许 watchdog 按总截止时间结案，但无法从串口队列撤回该对象。
于是串口线程稍后发送“已开始尝试”反馈时，调度器已经切换到另一个请求，形成
`request_id_mismatch`。第一层修复把这种错误变成了可见的有界停止，避免永久假运行；第二层修复
才消除竞态本身。

当前实现建立了单一所有权边界：

- queued 请求一旦交给串口队列，调度线程等待串口反馈，不再抢先终止；
- 串口线程是“是否真正开始发送”的最终裁决者；
- 串口线程在发送前发现总截止时间已过时，不发送 Modbus 帧，而是提交
  `deadline_exceeded`；
- 调度器只对这种满足截止时间条件的 queued 终态开放，其他越级状态转换仍拒绝；
- 已发送并进入 `waiting_response` 后，watchdog 才负责响应截止恢复。

这相当于把“取消一个还未发送的请求”放在真正持有该队列项的线程执行，避免两个线程分别认为
自己已经结束或开始了同一个请求。结构化事件 `request_expired_before_send` 使这种保护动作可以在
硬件日志中直接追踪。

## 9. 当前完成与未完成能力

已经完成：两只 TAS 地址持久化、三地址原始轮询、200ms根因对照实验、两层最小软件修复、
x86_64完整质量门、候选提交 `b35a01e25c95fb427fbfa165c4e7f3b030f73b8d` 的 ARM64 Release
构建与 `202/202` CTest，以及真实三从站正常基线、TAS-A/TAS-B 对称支路故障隔离和 MQTT
状态恢复。两个故障期间非目标从站最大成功间隔均低于10秒，调度反馈失败、状态转换错误和
MQTT发布失败均为0，因此 `CP-D=PASS`。

本次真实硬件结果也验证了 `request_expired_before_send` 的工程意义：目标从站断电后，重试可能
在全局200ms间隔等待期间越过总截止时间；串口线程会在真正写串口前终止该请求，而不会让迟到
反馈污染后续从站的调度上下文。TAS-A/TAS-B 场景分别触发17次和15次该事件，网关都持续服务
其他两个从站，并在目标恢复后自动回到 `online/fresh`。

尚未完成：T03 的 USB-RS485拔插、Mosquitto停止恢复、STM32 RESET、systemd/reboot，以及
T04 的一小时预跑和8小时硬件长稳。因此当前只能声明 T02/CP-D PASS，不能声明整个 G6 PASS。
