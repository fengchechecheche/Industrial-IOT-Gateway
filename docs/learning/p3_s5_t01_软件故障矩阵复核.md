> 面向读者：正在学习 C++、并发测试和工业网关可靠性验证的初学者  
> 对应实现：`tools/run_fault_matrix.py`、`tools/fault_matrix/`、`software.json`

## 1. 本工作块解决什么问题

S4 已经建立 F01–F15 软件故障矩阵，但“曾经通过”不能自动证明后续版本仍然可靠。S5-T01
在进入长稳测试前重新执行同一组主要故障，确认串口轮询、MQTT、队列、质量状态和关闭协议没有
因后续修改发生回退。

它验证的是 WSL2 中的软件链路，不测试 USB-RS485 电气层、STM32、真实传感器或 CAN。硬件未
到货不阻塞本工作块。

## 2. 所需术语和基础概念

- **故障注入（fault injection）**：主动制造断线、超时、坏帧、队列满等异常。
- **测试预言机（test oracle）**：机器判断结果是否正确的规则，例如进程退出码必须为零。
- **基线（baseline）**：已绑定具体提交并完成校验的参考结果。
- **探索性运行（exploratory run）**：用于定位实现或环境问题，但没有绑定可追溯提交。
- **正式运行（formal run）**：绑定 7～40 位十六进制提交 ID，且 `exploratory=false`。
- **恢复时间（recovery time）**：撤销故障后恢复到预期状态所需时间。本项目只在 F06、F10、
  F11、F13 中记录该指标。
- **数据竞争（data race）**：不同线程在缺少同步的情况下并发访问同一内存，并且至少一次是写。

## 3. 故障矩阵如何工作

`tests/data/fault_profiles/software.json` 冻结 F01–F15 的场景 ID、CTest 正则、超时和预期结果。
`tools/run_fault_matrix.py` 读取 profile，并为每个场景构造带 `--no-tests=error` 的 CTest 命令。
这样正则没有匹配到测试时不会被误判为成功。

runner 对每个场景依次执行：

1. 写入命令和 `scenario_started` 事件；
2. 创建独立进程会话并启动 CTest；
3. 到达超时时向整个进程组发送 SIGTERM，宽限期后仍未退出则发送 SIGKILL；
4. 保存 stdout、stderr、退出码和结构化事件；
5. 检查进程退出码以及必需的恢复时间；
6. 即使某个场景失败，也继续执行剩余场景；
7. 汇总 `summary.json`、`failures.json` 并生成 `SHA256SUMS`。

runner 的退出码是自动化接口：0 表示矩阵通过，2 表示参数或 profile 错误，3 表示构建目录错误，
4 表示场景失败，5 表示证据完整性错误。

## 4. 本项目中的数据流和线程角色

```text
software.json
    ↓
run_fault_matrix.py
    ↓ 每个 F01–F15 启动一个 CTest 进程
CTest → PTY 从站/本地 Mosquitto → gateway runtime
    ↓
stdout/stderr + 退出码 + FAULT_RECOVERY_TIME_MS
    ↓
events.jsonl / summary.json / failures.json / SHA256SUMS
```

网关运行时内部仍包含串口、质量处理和 MQTT worker 等线程。runner 位于被测进程外部，负责超时
和证据收集；它不持有网关内部锁，也不通过修改生产逻辑来伪造成功。

## 5. 关键类、接口和源码执行过程

### `process_manager.run_process()`

使用 `subprocess.Popen(..., start_new_session=True)` 建立新会话，因此超时时可以通过 `killpg()`
回收整个 CTest 进程组，避免只杀父进程而遗留 broker、PTY 或测试子进程。

### `EvidenceWriter`

负责生成 manifest、事件、场景摘要、失败清单和校验和。本次修复把 `stage` 与 `task` 参数化：
S4 仍可使用默认值，S5 必须显式写入 `S5` 和 `P3-S5-T01`，避免证据所属阶段错误。

### `run_scenarios()`

逐项运行场景并聚合状态。恢复指标通过
`FAULT_RECOVERY_TIME_MS=<非负整数>` 从测试输出解析；需要指标却没有输出时，即使测试进程退出
码为零，场景仍判定为失败。

### `MqttPublishSink::publish_direct()`

本轮 TSan 在 F10 捕获 Eclipse Paho publish delivery token 的完成回调与 token 析构并发。
当前实现有界保留 `active_publish_token_` 与 `previous_publish_token_` 两代对象。由于 MQTT
`max_inflight=1`，保留两代不会随运行时间无界增长，同时避免完成回调尚未返回时销毁其条件变量。

## 6. 为什么选择当前方案

- 继续使用已审核的 `software` profile，避免为了名称好看复制内容相同的 `release.json`。
- 正式运行绑定外部提供的提交 ID，但 runner 不自行调用 Git，符合权限边界。
- 采用结构化证据而不是只看终端最后一行，便于追踪场景、事件和失败。
- 恢复时间作为单次观察值保存，不直接宣传为生产 SLA。
- 对 Paho token 使用固定两代保活，而不是永久保存所有 token，避免把竞态修复变成内存无界增长。

## 7. 常见错误、失败模式和安全边界

- 把 `exploratory=true` 的 15/15 PASS 写成正式验收通过；
- profile 正则没有匹配到测试，却因缺少 `--no-tests=error` 被忽略；
- 场景失败后提前退出，导致矩阵覆盖不完整；
- 只杀 CTest 父进程，遗留子进程占用端口或 PTY；
- 只看 GoogleTest PASS，忽略 TSan 以非零状态报告的竞态；
- 无限保存异步 token 或消息，以生命周期安全为理由引入无界资源；
- 用一次恢复时间宣传确定性上界；
- 用 PTY/Mosquitto 回环结果代替真实 RS485、TLS 或跨主机网络证据。
