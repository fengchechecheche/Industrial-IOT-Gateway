# P3-S7-ARM64-T01 教程：树莓派原生构建与平台验证

## 1. 本工作块解决什么问题

项目此前已经在 Linux x86_64 环境完成软件 MVP 和正式质量门，但树莓派 4B 使用的是 ARM64
（AArch64）处理器。源码在 x86_64 上通过，并不自动意味着它能在 ARM64 上编译、链接和运行。

本工作块要回答：

> 同一份冻结源码能否在树莓派的真实 ARM64 用户空间中完成原生构建，并通过项目规定的软件质量
> 门、二进制身份检查和安全的安装暂存？

它不是硬件通信测试。树莓派本身是真实硬件，但没有接入 USB-RS485、Modbus 从站或 CAN 设备时，
只能证明计算平台和软件工具链，不足以证明现场总线能力。

## 2. 术语和基础概念

### 2.1 指令集架构（Instruction Set Architecture，ISA）

x86_64 和 AArch64 是不同的 64 位指令集。C++ 源码由编译器翻译为某一种架构的机器指令；x86_64
二进制不能直接当作 AArch64 二进制使用。

Linux 常见的三个身份字段分别来自不同层次：

- `uname -m`：当前内核看到的机器架构；
- `getconf LONG_BIT`：用户空间位数；
- `dpkg --print-architecture`：Debian/Ubuntu 软件包架构。

三者共同确认 `aarch64`、64 位和 `arm64`，可以避免“64 位内核配 32 位用户空间”等混合环境被
误当成标准 ARM64 基线。

### 2.2 原生构建（Native Build）

原生构建表示编译器就在目标架构上运行，并生成该架构的程序。本项目直接在树莓派上使用 GCC/Clang
和 Ninja 构建，因此不需要额外配置交叉编译器（Cross Compiler）。

原生构建的优点是目标系统头文件、动态库和运行时天然来自树莓派；代价是编译速度和存储性能通常
弱于桌面电脑。

### 2.3 ELF、动态链接和 ABI

ELF（Executable and Linkable Format）是 Linux 常用的可执行文件格式。三个工具各回答一个问题：

```bash
file gateway_app
readelf -h gateway_app
ldd gateway_app
```

- `file`：它是什么类型的文件、面向什么架构；
- `readelf -h`：直接读取 ELF 头中的 Class、Machine、Type 等字段；
- `ldd`：程序运行时需要加载哪些共享库，以及这些库能否找到。

只看到“编译成功”还不够。如果 `ldd` 出现 `not found`，程序部署后仍会因动态库缺失而无法启动。
本项目同时确认 Paho MQTT、yaml-cpp、libstdc++ 和 libc 来自 ARM64 系统库路径。

### 2.4 构建配置和质量门

不同构建目录承担不同角色：

- Debug：保留更多调试信息，便于发现逻辑问题；
- Release：启用优化，接近交付形态；
- ASan/UBSan：检测内存越界、释放后使用和未定义行为；
- TSan：检测线程间的数据竞争；
- clang-tidy：在不运行程序的情况下做静态分析；
- clang-format：验证 C++ 代码格式合同。

这些门不是重复劳动。编译器、优化级别和运行时插桩不同，能够暴露的缺陷也不同。

### 2.5 CTest

CTest 是 CMake 的测试驱动器。项目通过 `add_test()` 注册测试，CTest 负责发现、执行和汇总退出码。
本项目不仅检查“100% passed”，还核对期望测试数量、`LastTest.log` 中的逐项 PASS 数以及是否存在
`LastTestsFailed.log`。

本次还发现一个工程实践问题：在当前环境中，执行 `ctest -N` 查询测试清单会更新测试临时日志。
因此正式证据应先复制完整 `LastTest.log`，再做清单查询，不能把“清单存在”当成“测试执行过”。

## 3. 本项目中的执行链

```text
冻结提交与归档哈希
  → 树莓派环境、电源、散热和资源预检
  → Ubuntu ARM64 依赖
  → MQTT OFF Debug
  → MQTT ON + PTY Debug
  → Release
  → ASan/UBSan、clang-tidy、格式、Python、数据合同、TSan
  → file/readelf/ldd
  → DESTDIR 安装暂存
  → systemd unit 静态解析
  → summary/failures/SHA256SUMS
  → Release handoff 与限定清理
```

每一步都依赖前一步提供的身份或证据。若源码提交不一致，后面的测试即使 PASS，也不能归属于要验收
的候选版本。

## 4. 为什么要同时保留正、反 TSan 探针

TSan 由编译器插桩和运行库共同组成。只验证一个正常程序能启动，并不能证明工具真的会报告竞争。
因此本项目使用两个探针：

1. 安全探针通过 `std::atomic` 协作，应正常退出且不报告竞争；
2. 故意竞争探针让两个线程无同步地访问同一变量，应被 TSan 捕获并返回指定非零退出码。

两个结果同时满足后，项目测试中的“0 条 TSan 诊断”才有意义。故意竞争探针的报告是工具有效的
证据，不是项目源码缺陷。

本次最初缺少 AArch64 TSan runtime，因此链接阶段就失败。安装
`libclang-rt-18-dev:arm64` 后，运行库提供 `libclang_rt.tsan-aarch64`，条件门才具备执行基础。

## 5. `DESTDIR` 为什么不会污染系统

CMake 安装规则通常以 `/usr/local` 为安装前缀。直接执行系统安装会把程序、配置和 unit 写入真实
系统，增加覆盖已有文件的风险。

`DESTDIR` 在安装前缀外再添加一个临时根。例如逻辑目标
`/usr/local/bin/gateway_app` 会变成：

```text
<temporary-stage>/usr/local/bin/gateway_app
```

这样可以检查安装树的路径、权限、大小和哈希，同时不修改真实 `/usr/local` 或 `/etc`。本次暂存
包含 9 个文件，执行文件为 `0755`，配置、unit 和文档为 `0644`。

`DESTDIR` 证明的是“安装规则能够生成正确文件树”，不是“系统服务已经成功部署”。

## 6. systemd 静态解析和真实运行的区别

`systemd-analyze verify` 可以检查 unit 的未知字段、缺失依赖和不可执行命令等问题。本项目结合
`--root=<temporary-stage>`，让解析器在暂存根中检查 unit 和 `gateway_app`。

静态解析退出 0 只能说明 unit 在该文件树中能够通过解析。它没有覆盖：

- 用户和组是否已创建；
- `/etc` 中的正式配置是否正确；
- 服务能否启动、重启和开机自启；
- SIGTERM、异常退出、配置错误等原生 systemd 场景；
- 串口权限和真实设备路径。

因此本工作块保持 `arm64_systemd_validated=false`。

## 7. 证据是如何从测试结果生成的

正式 evidence 包含环境、软件包、源码身份、六套 `LastTest.log`、构建矩阵、二进制身份、动态依赖、
安装清单、`failures.json`、`summary.json` 和 `SHA256SUMS`。

判定流程是：

1. 从真实日志计算测试数、失败文件和 Sanitizer 诊断数；
2. 从 ELF、动态库和安装树计算架构、路径、权限与文件哈希；
3. 任一必需条件失败就向 `failures.json` 添加原因；
4. 只有失败数组为空，才生成最终 PASS 标记；
5. 最后用 `sha256sum -c` 复核证据文件没有在生成后发生变化。

这种方式比人工写一句“测试通过”更可信，因为每个结论都能追溯到机器生成的数据。

## 8. Release handoff 的作用

质量门构建目录体积较大，而且都能从冻结源码重新生成。工作块结束后，项目删除 Debug、ASan、
clang-tidy 和 TSan 等可重建目录，保留：

- 冻结候选源码；
- 原始正式 evidence；
- Release 原构建；
- 与 Release 构建树逐文件一致的私有 handoff。

handoff 为后续 ARM64 工作提供稳定输入，但它还不是正式 Release bundle。bundle 仍需要独立的清单、
支持平台声明、复现和发布边界，所以 `arm64_release_bundle_ready` 保持 false。

## 9. 电源、温度和构建并行度

树莓派在编译期间持续检查 SoC 温度和 `get_throttled`。后者是位图，能够表示当前或历史欠压、限频、
降频和软温度限制。

本项目当前规则是：

- 构建使用 `-j4`；
- 70～79°C 只记录 WARN，不自动改为 `-j2`；
- 达到 80°C、出现当前欠压/降频、OOM 或 I/O 错误时，停止启动新任务。

本次 CP8 前后温度约 47～49°C，`get_throttled=0x0`。这些值证明本次运行没有受到已检测到的电源
或热约束，但不能永久保证换电源、换外壳或换环境后仍然相同。

## 10. 常见错误、失败模式和安全边界

### 10.1 把架构字符串当成全部证据

只运行 `uname -m` 不足以证明用户空间、软件包和最终二进制都是 ARM64。应同时检查用户空间位数、
包架构、ELF 头和动态依赖。

### 10.2 把“测试清单”当成“测试结果”

`ctest -N` 只列出测试，不执行测试。正式证据必须来自完整 CTest 运行及真实退出码。

### 10.3 把工具链缺失当成代码失败

TSan runtime 缺失发生在链接阶段，不能推断项目存在数据竞争。应记录为工具链 blocker，安装后从
正、反探针重新开始。

### 10.4 直接安装到系统

未经部署授权，不应执行写入真实 `/usr/local`、`/etc` 或 systemd 状态的操作。先使用唯一
`DESTDIR` 暂存根，完成静态验证后删除。

### 10.5 清理范围过宽

不能对工作区根、`$HOME` 或 `/tmp` 使用宽泛递归删除。应解析每个绝对路径，确认它属于本次明确
创建的 stage、探索 evidence 或可重建构建目录后再删除。
