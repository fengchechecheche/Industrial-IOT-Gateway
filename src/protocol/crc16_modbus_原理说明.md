# CRC16/Modbus 当前实现原理说明

## 1. 这段实现解决什么问题

`crc16_modbus.cpp` 用于计算 Modbus RTU 帧的 CRC16 校验值。发送端用它为地址、功能码和数据字段生成校验值；接收端对收到的非 CRC 字节重新计算，并与帧尾两个 CRC 字节比较，从而检测传输中的比特错误。

当前实现只负责“根据一段字节计算一个 16 位数值”，不负责：

- 把 CRC 追加到帧尾；
- 将 CRC 拆分成线上传输字节；
- 判断一段输入是否构成完整 Modbus RTU 帧；
- 处理功能码、寄存器地址或异常响应。

这些边界使 CRC 算法不依赖 codec、parser、串口或业务层，可以单独测试和复用。

## 2. 当前使用的 CRC 参数

当前实现采用冻结协议文档规定的标准 CRC16/Modbus 参数：

| 参数 | 当前取值 | 含义 |
|---|---:|---|
| 宽度 | 16 位 | CRC 寄存器保留 16 位 |
| 初始值 | `0xFFFF` | 处理第一个输入字节前的寄存器值 |
| 正向多项式 | `0x8005` | 常见的数学表示 |
| 反射多项式 | `0xA001` | `0x8005` 按位反射后的逐位实现形式 |
| 输入反射 | true | 每个字节从最低有效位方向参与运算 |
| 输出反射 | true | 与右移、反射多项式的实现方向一致 |
| 最终异或值 | `0x0000` | 计算结束后不再异或其他常量 |
| 线上顺序 | 低字节在前 | 这是序列化规则，不是 CRC 数值本身的一部分 |

头文件中的两个常量分别对应初始值和反射多项式：

```cpp
inline constexpr std::uint16_t kCrc16ModbusInitialValue = 0xFFFFU;
inline constexpr std::uint16_t kCrc16ModbusReflectedPolynomial = 0xA001U;
```

## 3. 为什么当前项目不使用 `using namespace std;`

初学 C++ 时常见下面的写法：

```cpp
using namespace std;
```

教学示例使用它，通常是为了少写 `std::`，让注意力集中在当时讲解的语法上。但它会把整个 `std` 命名空间中的名称引入当前作用域。在工程代码逐渐引入更多标准库头文件、第三方库和项目模块后，`count`、`distance`、`begin`、`end`、`data` 等常见名称可能产生歧义，代码阅读者也不能从名称本身立即判断其来源。

尤其不能在公共头文件中使用 `using namespace std;`。任何包含该头文件的源文件都会被动受到名称导入影响，污染范围超出了 CRC 模块本身，而且可能因为以后新增一个头文件或升级标准库而出现原本不存在的名称冲突。

当前接口因此明确写成：

```cpp
std::uint16_t crc16_modbus(const std::uint8_t *data, std::size_t size) noexcept;
```

这里：

- `<cstdint>` 提供 `std::uint8_t` 和 `std::uint16_t`；
- `<cstddef>` 提供 `std::size_t`；
- `<iostream>` 提供 `std::cin`、`std::cout`、`std::cerr` 等输入输出流，与定宽整数类型无关，本模块没有输入输出需求，因此不应引入；
- 显式保留 `std::` 能直接说明类型来自标准库，并避免名称污染。

即使包含 `<iostream>`，也不会因此自动省略 `std::`。如果某个很小的局部作用域确实频繁使用单个名称，可以精确引入：

```cpp
void example() {
  using std::uint16_t;
  uint16_t value = 0U;
}
```

这种写法只引入一个明确名称，并把影响限制在函数内部；当前 CRC 接口较短，直接使用 `std::` 更清楚。

## 4. 为什么使用 `0xA001` 和右移

CRC 可以按最高有效位优先或最低有效位优先两种方向实现。Modbus RTU 的常用逐位算法采用反射形式：输入字节先与 CRC 寄存器低 8 位异或，然后检查最低有效位，并让寄存器向右移动。

在这种方向下，必须使用正向多项式 `0x8005` 的反射形式 `0xA001`。因此下面三项是配套的，不能只替换其中一项：

1. 检查最低位 `crc & 0x0001U`；
2. CRC 寄存器右移 `crc >>= 1U`；
3. 条件异或反射多项式 `0xA001`。

如果改成检查最高位和左移，就应改用与该方向匹配的多项式表达和处理规则，否则结果不会是 CRC16/Modbus。

## 5. 为什么每次处理一个字节，而不是两个字节

“CRC16”中的 16 表示 CRC 余数和寄存器宽度为 16 位，并不表示输入必须每次取 16 位。CRC 本质上处理连续比特流，每个输入比特都会更新一次 16 位 CRC 寄存器。当前实现按字节读取，只是将连续比特按计算机和 Modbus RTU 最自然的 8 位单位分组；每读入一个字节，内层仍执行 8 次逐位更新。

需要区分三个概念：

| 概念 | 当前取值 | 作用 |
|---|---:|---|
| CRC 宽度 | 16 位 | 决定寄存器和最终校验值宽度 |
| 输入单位 | 8 位 | 通过 `std::uint8_t` 顺序读取 Modbus 字节流 |
| 每个输入单位的更新次数 | 8 次 | 让该字节的每个比特参与多项式运算 |

Modbus RTU 帧表现为有顺序的字节流，例如：

```text
01 03 00 00 00 02
```

CRC 必须依次处理 `01`、`03`、`00`、`00`、`00`、`02`。按字节实现有以下好处：

- 与串口接收、帧缓存和协议文档中的字节顺序直接对应；
- 支持任意长度，包括奇数字节数；
- 不依赖 CPU 如何把两个相邻字节解释成一个 16 位整数；
- 不需要额外处理最后剩余的单字节；
- 更容易逐项对照协议黄金向量。

算法也可以优化成一次读取两个字节，但必须明确先处理哪个字节、正确处理其中 16 个比特、处理奇数长度，并保证不受主机大小端影响。数学上它依然按原顺序处理这两个字节中的全部比特，只是改变了实现分组，不能因为 CRC 结果是 16 位就直接把两个输入字节当成一个主机端 `uint16_t`。

CRC32 通常也按字节读取输入，这同样说明 CRC 名称中的位数描述的是结果宽度，而不是输入分组宽度。

## 6. 代码执行过程

函数接口为：

```cpp
std::uint16_t crc16_modbus(const std::uint8_t *data, std::size_t size) noexcept;
```

其执行过程可以概括为：

```text
crc = 0xFFFF

依次处理每个输入字节：
    crc = crc XOR 当前字节

    重复 8 次：
        记录 crc 的最低位
        crc 右移 1 位
        如果原最低位为 1：
            crc = crc XOR 0xA001

返回 crc 的 16 位数值
```

### 6.1 初始化

```cpp
auto crc = kCrc16ModbusInitialValue;
```

`kCrc16ModbusInitialValue` 的类型明确为 `std::uint16_t`，因此 `auto` 推导出的 `crc` 也是 16 位无符号整数。空输入不会进入循环，所以直接返回 `0xFFFF`，这也是当前空输入测试的期望值。

### 6.2 将一个输入字节混入 CRC

```cpp
crc ^= data[index];
```

输入字节与当前 CRC 的低 8 位异或。异或会让当前字节的每一位进入后续 8 次多项式除法步骤。

### 6.3 逐位执行 8 次更新

```cpp
const bool least_significant_bit_is_set = (crc & 0x0001U) != 0U;
crc >>= 1U;
if (least_significant_bit_is_set) {
  crc ^= kCrc16ModbusReflectedPolynomial;
}
```

每个输入字节有 8 位，因此内层循环固定执行 8 次：

- 原最低位为 `0`：只右移；
- 原最低位为 `1`：右移后再异或 `0xA001`。

条件异或相当于在 GF(2) 上进行多项式长除法。GF(2) 中的加减法都等价于异或，不需要普通整数的进位或借位。

## 7. 单字节示例

以输入字节 `00` 为例：

1. 初始 CRC 为 `FFFF`；
2. 混入字节：`FFFF XOR 00 = FFFF`；
3. 依次执行 8 次最低位判断、右移和条件异或。

| 位步骤 | 更新后的 CRC |
|---:|---:|
| 1 | `DFFE` |
| 2 | `6FFF` |
| 3 | `97FE` |
| 4 | `4BFF` |
| 5 | `85FE` |
| 6 | `42FF` |
| 7 | `817E` |
| 8 | `40BF` |

所以 `crc16_modbus({0x00}, 1)` 返回数值 `0x40BF`，与单元测试中的独立参考值一致。

## 8. 返回数值与线上字节顺序

函数返回的是数值，而不是已经排好顺序的两个字节。例如，对以下不含 CRC 的请求内容计算：

```text
01 03 00 00 00 02
```

函数返回：

```text
0x0BC4
```

Modbus RTU 在线上规定低字节先发，因此序列化层应追加：

```text
C4 0B
```

完整帧才是：

```text
01 03 00 00 00 02 C4 0B
```

接收时则用下面的方式从帧尾恢复数值，再与重新计算的 CRC 比较：

```cpp
received_crc = low_byte | (high_byte << 8U);
```

将“CRC 数值计算”与“线上低字节先发”分开，可以避免算法内部偷偷依赖主机大小端，也使接口含义更加明确。

## 9. 接口约束

- `size == 0` 时允许 `data == nullptr`，函数不会解引用指针，并返回初始值 `0xFFFF`。
- `size > 0` 时，调用方必须保证 `data` 非空，并且至少指向 `size` 个可读字节。
- 调用方应传入不包含帧尾 CRC 两字节的内容；若把原 CRC 字节也传入，计算语义就不再是当前测试采用的“生成或比较帧 CRC”。
- 函数使用 `noexcept`，内部不分配内存、不抛出异常，也不修改输入数据。

## 10. 为什么当前选择逐位实现

当前采用逐位实现，而不是 256 项查表实现，主要因为：

- 代码短，参数和运算方向容易审查；
- 不需要维护额外查找表，也没有表生成错误的风险；
- 空间开销为常数；
- 当前 Modbus RTU 帧规模较小，逐字节 8 次迭代足以满足协议内核阶段的需求。

对于 `n` 个输入字节，时间复杂度为 `O(8n)`，通常简写为 `O(n)`；额外空间复杂度为 `O(1)`。若后续基准测试证明 CRC 是真实性能瓶颈，可以在保持同一 API 和测试向量不变的情况下替换为查表实现，但不能只凭推测提前优化。

## 11. CRC16 查表法为什么是 256 项

常见 CRC16 查表法选择一次处理一个字节。一个字节有 `2^8 = 256` 种可能值，即 `0x00～0xFF`，所以可以提前保存这 256 种低 8 位状态分别经过 8 次逐位更新后的结果。

256 与 CRC16 的 16 位结果宽度没有直接关系：表项数量由“一次预计算多少输入位”决定，每个表项的内容才是 16 位 CRC 值。CRC32 的普通按字节查表同样通常有 256 项，只是每项保存 32 位结果。

### 11.1 表项如何生成

对每个索引 `0x00～0xFF`，从该索引值出发，完全按照当前逐位实现的最低位判断、右移和 `0xA001` 条件异或规则执行 8 次：

```cpp
std::array<std::uint16_t, 256> make_crc16_modbus_table() {
  std::array<std::uint16_t, 256> table{};

  for (std::size_t index = 0; index < table.size(); ++index) {
    auto value = static_cast<std::uint16_t>(index);

    for (unsigned int bit = 0; bit < 8U; ++bit) {
      if ((value & 0x0001U) != 0U) {
        value = static_cast<std::uint16_t>((value >> 1U) ^ 0xA001U);
      } else {
        value >>= 1U;
      }
    }

    table[index] = value;
  }

  return table;
}
```

表的前几项为：

```text
table[0x00] = 0x0000
table[0x01] = 0xC0C1
table[0x02] = 0xC181
table[0x03] = 0x0140
```

例如 `table[0x01]` 表示低 8 位状态 `0x01` 经过一整个字节对应的 8 次 CRC 更新后，预计算结果为 `0xC0C1`。

### 11.2 运行时为什么这样索引

逐位算法处理一个字节时首先执行：

```cpp
crc ^= current_byte;
```

输入只有 8 位，因此当前字节只先影响 CRC 的低 8 位。决定接下来 8 次最低位分支的状态就是：

```cpp
(crc ^ current_byte) & 0x00FFU
```

这个值的范围正好是 `0x00～0xFF`，因此可以直接作为 256 项表的索引。

### 11.3 查表更新公式从哪里来

GF(2) 中的加减法都等价于 XOR，CRC 变换具有线性。对当前字节执行 8 次更新后，可以把旧 CRC 的影响拆成两部分：

1. 旧 CRC 高 8 位经过 8 次右移，形成 `crc >> 8U`；
2. 旧 CRC 低 8 位与当前输入字节混合后的影响，已经保存在对应表项中。

两部分通过 XOR 合并：

```text
new_crc = (old_crc >> 8)
          XOR table[(old_crc XOR current_byte) AND 0xFF]
```

对应 C++ 写法是：

```cpp
const auto table_index =
    static_cast<std::uint8_t>((crc ^ current_byte) & 0x00FFU);

crc = static_cast<std::uint16_t>((crc >> 8U) ^ table[table_index]);
```

这样，一次查表、一次右移和一次异或就替代了原来的 8 次逐位判断与更新。

### 11.4 为什么也可以不是 256 项

表大小取决于每次预计算的位数：

| 每次处理位数 | 表项数量 | 特点 |
|---:|---:|---|
| 1 位 | 2 项 | 接近逐位算法 |
| 4 位 | 16 项 | 表较小，但每字节查两次 |
| 8 位 | 256 项 | 常见的速度与空间折中 |
| 16 位 | 65536 项 | 一次处理两字节，但表很大 |

CRC16 的 256 项表以 `std::uint16_t` 保存时通常占 `256 × 2 = 512` 字节，规模较小，又与字节流自然对应，因此最常见。

### 11.5 CRC 表不能跨算法直接复用

查找表取决于多项式、移位方向、输入反射方式和寄存器宽度。当前 Modbus 算法使用“检查最低位、右移、异或 `0xA001`”的反射规则，因此必须使用按同一规则生成的表，不能直接替换成 CRC-CCITT、CRC16/XMODEM 等其他算法的表。

初始值 `0xFFFF` 通常也不固化在单个表项中，而是在处理整段输入前设置 CRC 寄存器。表只预计算一个字节对应的状态变换。

## 12. 当前验证覆盖

现有测试验证了：

- 空输入：`0xFFFF`；
- 单字节 `00`：`0x40BF`；
- 标准校验串 `123456789`：`0x4B37`；
- 254 字节边界输入：`0x576C`；
- 单比特翻转后 CRC 改变；
- 冻结协议中的 19 条帧向量及低字节先发规则。

这些测试证明当前实现与已冻结的 CRC 参数和项目协议向量一致，但 CRC 只能检测传输错误，不能提供加密、身份认证或防恶意篡改能力。
